# 联机服务端与运营层规划（登录 / 数据库与持久化 / 大厅 / 房间 / 社交 / 聊天）

> 制订日期：2026-09-14。关系：上承《状态同步实施方案》§4.6（服务选型判据）与 §13（数据归档与持久化）、下接《联机同步策略设计》§4（**接缝清单**）与《联机Demo设计》。**本文把"接缝清单"落实为可实施规划**。
> 一句话定位：**对局服保持薄**（只做权威 Sim + 广播 + 归档），账号/大厅/进度/社交/聊天全部是**新增的独立服务进程**。

## 1. 服务拓扑与选型

### 1.1 进程划分（形态钉死：对局服保持薄）

```
客户端
 ├─ LiteNet（信令 + 对局输入/快照）  ←→ RoomServer（对局服，薄）
 └─ HTTP/JSON（账号/大厅/进度/社交/聊天）←→ 业务服务群
                                             ├─ AuthService    登录/账号/token 签发
                                             ├─ LobbyService   大厅/房间目录/匹配/房间注册表
                                             ├─ ProfileService 玩家进度/结算变更单（权威）
                                             ├─ ChatService    聊天/社交（起步同进程）
                                             └─（后置）OpsCollector  指标时间序列
     RoomServer ←─ 内部 Admin API ←─ LobbyService（房间创建/销毁）
```

- **对局服（RoomServer）**：只做 ①token **验签**（不查库）②房间生命周期 ③权威 Sim ④快照广播 ⑤归档写出。**不认识账号/大厅/DB**
- **业务服务**：每服务独立进程、各自选型；MVP 可同机多进程
- **跨进程房间路由**：`room_registry`（房间 → 进程 endpoint 映射，§4）

### 1.2 协议与选型

| 链路 | 协议 | 理由 |
| --- | --- | --- |
| 客户端 ↔ 对局服 | **LiteNet + protobuf**（既定） | 60Hz 热路径；协议单源（客户端/服务端共用程序集） |
| 客户端 ↔ 业务服务 | **HTTP + JSON**（内网/公网均可） | 低频信令；可调试性好；**不涉及与客户端双写**（不碰 LiteNet 红线） |
| 服务间（Lobby → RoomServer Admin API） | **HTTP + JSON** | 同上；起步简单 |
| 数据库 | **PostgreSQL**（推荐）+ Npgsql/Dapper；**MVP 降级 = SQLite 单文件**（零运维） | .NET 8 原生友好；关系型契合进度/流水/归档元数据 |
| 缓存/注册表 | MVP：**进程内内存**；规模化：**Redis** | room_registry/匹配队列/会话 |

> **Fantasy 复核**：§4.6 的触发条件（要养复杂业务服务）**现已命中**——Auth/Lobby/Profile 是其主场。但形态仍是「新增独立服务进程、对局服保持薄」；是否用 Fantasy 实现首个业务服务，留作**实施时选型**（本文不锁定）。协议双写成本不涉及（服务间 HTTP）。

## 2. 登录与账号

### 2.1 两种形态（MVP 先做前者）

| 形态 | 做法 | 时机 |
| --- | --- | --- |
| **游客账号（MVP）** | 客户端生成/持久化 `deviceId`（FileSys）→ `AuthService.Login(deviceId)` → 返回 `{playerId, token, nickname, avatar}` | M13 |
| 正式账号 | 账号密码 / 第三方（Steam/微信/Apple）→ `IAuthProvider` **策略位**（多实现，不动流程） | 后置 |

### 2.2 流程（token 自包含 = 对局服保持薄的关键）

```
① Client → AuthService.Login(deviceId | credential)
② AuthService 校验/建号 → 签发 token（自包含：playerId + 过期 + 签名；HMAC/Ed25519）
③ Client 持久化 token（FileSys，降级为"镜像缓存"的既有纪律）
④ Client → RoomServer.Join(roomId, token, buildHash)
⑤ RoomServer **本地验签**（持有公钥/密钥，不查库）→ 通过则进房
⑥ 断线重连：token 复用（或换取短时重连票据）
```

- **token 不进 Sim**（不参与确定性）；`buildHash` 校验照旧（防跨构建混房）
- 服务端与客户端的"版本一致性"链路不变（§4.5 关键机制 5）

## 3. 数据库与数据持久化

### 3.1 三层归属（承《状态同步实施方案》§13，不动）

| 层 | 归属 | 载体 |
| --- | --- | --- |
| 运行期状态 | AuthSim / 环形缓冲 | 内存（不落盘） |
| **对局事实** | `MatchArchive`（种子 + 输入 = 整场） | 文件/对象存储（§13.2） |
| **玩家事实（权威）** | **ProfileService** | 数据库（本文新增 schema） |
| 运维事实 | Ops 指标 | 滚动日志 →（后置）时间序列 |
| 客户端本地 | FileSys | **镜像缓存 + 玩家偏好**（既有决议，永不权威） |

### 3.2 首版 schema（草案）

```sql
player            (player_id PK, device_id UNIQUE, nickname, avatar, created_at, last_login_at)
player_progress   (player_id PK, exp, level, currency, updated_at)              -- 当前值
progress_ledger   (ledger_id PK, player_id, match_id, delta_json, created_at,
                   UNIQUE(player_id, match_id))                                  -- 幂等流水（先流水后余额）
match_archive     (match_id PK, seed, players_json, build_hash, sim_version,
                   final_checksum, archive_path, flagged, created_at)
room_registry     (room_id PK, process_id, endpoint, mode, sync, capacity,
                   player_count, state, updated_at)                              -- 大厅 ↔ 对局服的房间发现
friend            (player_id, friend_id, state, created_at, PRIMARY KEY(player_id, friend_id))
chat_message      (channel_id, sender_id, content, created_at)                   -- 后置；房间频道可不落库
```

### 3.3 一致性与运维

- **结算幂等**：`UNIQUE(player_id, match_id)` + "先写流水、后改余额" → 重复提交只落一次、可重放修复
- **变更单来源**：对局服在结算时调用 `ProfileService.Apply(progressDelta)`（或先落归档、由 ProfileService 拉取——**二选一在 M13 定**）
- **保留策略**（§13.2 既有）：普通归档 7 天滚动，被标记/被举报长期保留
- **备份**：数据库按日备份；归档文件按日期分目录

---

### 3.4 数据库选型：为什么默认 PostgreSQL 而不是 MongoDB（2026-09-14 定）

**结论：默认 PG（MVP 降级 SQLite）+ 归档走文件/对象存储 + Redis（可选）；MongoDB 有正当位置，但不是这套数据的默认。**

按**数据形态**逐个判（选型跟着数据走，不跟着潮流走）：

| 数据 | 形态特征 | 最佳载体 | Mongo 合适吗 |
| --- | --- | --- | --- |
| 玩家进度 + 流水 | 关系型小行 + **幂等唯一键 + 事务**（结算不能重复扣） | **PG / SQLite**（唯一约束 + 事务是天然工具） | ⚠️ 能做（唯一索引 + 幂等键），但事务/约束心智更重 |
| 对局归档 | **大 blob**（种子 + 输入 ≈ 1MB/场，冷数据） | **文件 / 对象存储**（§13.2 既有：按日目录 + 原子写） | ❌ 进库会撑大库；GridFS 可用但不如对象存储省 |
| 房间注册表 | **易失、高频、带 TTL** | 进程内内存 / **Redis** | ❌ 与文档库无关；任何持久库都不是它的家 |
| 好友 / 组队 | 关系型、小、强约束 | PG | ⚠️ 可做，无优势 |
| **聊天消息** | **append-only、量大、schema 松散** | **MongoDB 的正位置**（文档模型 + 分片） | ✅ **这是 Mongo 真正合适的地方** |
| Ops 指标 | 时序 | 滚动日志 →（后置）时序库 | ⚠️ 勉强 |

**MongoDB 的两个正当入口**（明确写清，避免"一刀切否定"）：
1. **聊天/消息类**（量大、松散、追加写）——M15 若聊天量上来，Mongo 比 PG 顺手
2. **若采用 Fantasy** 作为业务服务框架——其自带 MongoDB 组件，Mongo 会成为它的**默认路径**（那时是"框架选型带动持久化"，而非为数据形态选型）

**为什么 demo 阶段不必纠结**：几十个玩家、数据形态简单、无并发写压力 → **M13 起步用 SQLite（零运维）+ 文件归档**即可；PG / Mongo / Redis 都是规模化后的事。**判据留档，选型在 M13 定**（不预先引入任何 DB 依赖）。

## 4. 大厅与房间（接缝第 1/2 条）

### 4.1 房间创建（此前完全无答案的问题）

```
Client → LobbyService.CreateRoom(mode, sync, capacity)
  → LobbyService 按 room_registry 选一个健康对局服进程（负载最低）
  → 调该进程内部 Admin API: POST /rooms {mode, sync, capacity}
  → 返回 {roomId, joinToken}  → LobbyService 登记 room_registry
  → Client 用 (roomId, joinToken) 走 LiteNet Join（对局服验签）
```

- 对局服的 Admin API **只做房间生命周期**（创建/销毁/查询），不认识账号
- 健康检查：LobbyService 心跳各对局服（心跳超时 → `room_registry` 标记不可用）

### 4.2 房间发现与匹配

| 能力 | MVP（M14） | 后置 |
| --- | --- | --- |
| 发现 | 房间号 / 好友码直连 | 房间列表（按 mode/延迟排序） |
| 匹配 | 手动（好友码） | **快速匹配队列**：按 `(mode, sync, MMR)` 分桶，满员建房（LobbyService 内） |
| 组队进房 | 好友码邀请 | 队伍（team 表）后进同一房间 |

### 4.3 跨进程路由

- 房间**不跨进程迁移**（既定）；大厅只负责把客户端导向正确进程
- 对局服进程重启 → `room_registry` 条目超时淘汰（对局中断，按 §5.6 重连语义不可恢复时提示重开）

## 5. 社交与聊天（接缝第 4 条）

| 面 | MVP（M15） | 后置 |
| --- | --- | --- |
| **好友** | 请求/接受/删除/列表（`friend` 表 + LobbyService API）；在线状态来自会话表 | 黑名单、备注、最近同玩 |
| **组队** | 好友码拉人进同房间 | 队伍系统（邀请/队长/自动组队进匹配） |
| **聊天** | `ChatService`（起步与 Lobby 同进程）：**世界 / 私聊 / 系统** 三频道；敏感词表过滤；世界与私聊入库 | 房间频道（可由对局服转发降低延迟）、语音、举报流程 |
| 客户端接入 | `Bridge.chat` / `Bridge.social` 门面（**新增门面须按 §4.3 白名单纪律登记**） | — |

**边界**：聊天**不进 Sim**（纯服务层，与服务端时间无关）；战斗内快捷消息若要走对局通道，须作为**输入的一部分**（进 `InputFrame`）而非旁路——这条在实施时按需要再定。

## 7. 与既有决策的对齐检查

- ✅ **框架层不感知**：LiteFramework 只放契约；这些服务是**业务侧进程**（与 §4.6 形态一致）
- ✅ **对局服保持薄**：token 本地验签、Admin API 只做房间生命周期、不认识 DB
- ✅ **客户端权威边界**：进度变更单由服务端产出并持久化；客户端 FileSys 是镜像缓存
- ✅ **协议单源不受影响**：LiteNet 只用于客户端 ↔ 对局服；业务服务走 HTTP
- ⚠️ **新增门面需登记**：`Bridge.chat/social` 属新增 Lua 门面（§4.3 白名单纪律）
- ⚠️ **隐私与合规**（demo 阶段不阻塞）：设备 ID 采集、聊天内容留存需在上线前评审
