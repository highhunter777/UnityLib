> **M11 交付物**：本文的 Sim 侧数据形态 + 控制器 + 输入服务 + 相机（对照 §9 M11 行：`SimView` / 和解重对齐 / **输入采集** / **`PlayerController`（走位/瞄准/键位重绑）** / 相机 / 地图装配）。

## 0. 一句话结论

| 问题 | 结论 |
|---|---|
| 角色状态机能用框架状态机吗？ | **判定相关的不能**（Sim 层红线 + 快照约束）；**表现相关的可以**（View 侧平面机） |
| 移动机要上状态机吗？ | **不要**——它是速度的**连续映射**（idle/walk/run 由速度推导），不是"迁移" |
| 战斗机怎么实现？ | Sim 侧 = **单主动作槽 + `ActionState` 数据 + `canBeInterruptedBy` 表规则**（不是类状态机）；View 侧订阅帧事件播表现 |
| 角色控制怎么做？ | 输入设备 →（View）意图换算 → `SimInputFrame` →（Sim）Movement/Shooting 判定 → 帧事件/快照 →（View）表现 + 相机。**Sim 只收世界量，不认相机/设备** |
| 瞄准用什么表示？ | **已定（2026-09-17）：`Aim` 方向（`AimX/AimZ`）**；`EntitySlot.Yaw` 降为 Sim 内派生（`SimTrig` 查表）。见 §7-1 的实施清单 |

## 1. 三层边界（所有决定的根）

| 层 | 装什么 | 框架状态机 | 依据 |
|---|---|---|---|
| **Sim（判定）** `LiteSim.Core` | 动作槽 / 动作阶段 / 受击硬直 / 死亡、移动物理（`Pos`/`Vel`/`Yaw`） | ❌ **用不了**（也不该用） | `LiteSim.Core.asmdef` = `references: []` + `noEngineReferences: true`，csproj 无 ProjectReference → **"Sim 不引用 LiteFramework"是红线**（状态同步 §14.1）。更硬的一条：**Sim 的状态必须是快照数据**（值类型、可 `CopyTo`、回滚后逐位一致），不可能是状态单例对象图 |
| **View（表现）** `LiteSim.View` / `LiteGame` | 动画层与分级、战斗表现、特效/音效、相机、HUD | ✅ **可以**（`StageMachine` 平面机） | 纯表现编排，无回滚约束；且"表现不携带判定"（《UI扩展能力设计》§1.5） |
| **输入/意图** | 玩家想做什么 | — | 是**数据**（`SimInputFrame`），不是状态机 |

**推论**：Sim 侧的"角色状态机"要写成「**数据 + 表驱动规则**」；框架状态机只在 View 侧有用武之地。

## 2. Sim 侧：角色状态 = 数据 + 表（不是状态机）

### 2.1 `ActionState` 与单主动作槽

```csharp
// LiteSim.Core（零依赖；随快照走、可 CopyTo、回滚一致）
public enum ActionPhase : byte { None = 0, Windup = 1, Active = 2, Recovery = 3 }

public struct ActionState            // 每实体一个定长小结构（放 EntitySlot 或 CustomData[32]）
{
    public int ActionId;             // 0 = 无动作（**单主动作槽**：一个实体同时只有一个主动作）
    public int StartFrame;           // 整数帧（判定按帧触发，§3.9）
    public ActionPhase Phase;
    public long SourceId;            // 触发者（投射物/技能来源；无来源为 0）
}
```

- **为什么不是类状态机**：状态对象是**对象图**，进不了快照；`StageMachine` 持有"当前阶段对象"，`CopyTo` 复制不了它。Sim 的状态迁移必须由**整数帧 + 表**推进，才能在回滚重放后进度一致（§动作与特效设计 §3 验收第 3 条）。
- **一个槽，不是一棵树**：冲刺 + 技能同帧乱套的解法是**单槽 + 抢槽仲裁**，不是层级/并行状态。

### 2.2 迁移规则 = 表（`tb_action_num` / `tb_action`）

| 表 | 管什么 |
|---|---|
| `tb_action_num` | 数值：各阶段时长（帧）、判定帧、伤害/位移参数（策划改、可 diff、可热更） |
| `tb_action` | 时序与分类：`category`（skill/dash/interact/death/…）+ `tracks`（时间轴导出列）+ `canBeInterruptedBy`（中断规则位） |

- **推进**：`ActionSystem` 每帧按 `Frame - StartFrame` 落到对应 `Phase`，到 `Active` 帧触发判定（写命令/帧事件）。
- **中断**：新动作请求来时查 `canBeInterruptedBy`（如"冲刺可被受击打断、技能施法中不可被打断、交互读条移动即取消"）→ 允许则抢槽（旧动作直接结束，不播后摇）。
- **移动与动作的互斥**：按 §1.4 的**占槽互斥接口**耦合（例：冲刺期间移动输入被动作接管；移动输入取消交互读条）——**两条 System 不互相嵌套**。

### 2.3 移动机：为什么不该是状态机

| | 移动（Locomotion） | 战斗（Combat） |
|---|---|---|
| 性质 | **连续**（速度/落地的连续量） | **离散**（有前摇/持续/后摇的时序动作） |
| 表现需求 | idle/walk/run/sprint/fall 的**分级** | 逐动作的动画/特效/音效 |
| 判定需求 | 只有 `Pos`/`Vel` 的积分（MovementSystem 已有） | 判定帧、中断、抢槽 |
| 结论 | Sim 侧**无状态**（只有物理量）；View 侧是**阈值映射**，不是迁移 | Sim 侧 `ActionState`；View 侧订阅帧事件 |

**判据**：**状态迁移由"事件/条件"驱动才值得上状态机；纯连续映射不值得**（上了只是把 `if` 换成状态类，还多一层同步）。所以：**别给移动做状态机**——一个 `Speed → Animator 参数` 的分级器就够。

### 2.4 多状态怎么办：**四类归属** + 三轴关系（2026-09-17 补）

用户列举的"空闲/走路/慢跑/奔跑/冲刺/停步/起步/喝药/交互/眩晕"**不是一个状态机的状态集**——它们分属四类机制，各归各的扩展点：

| 你列的状态 | 类别 | 归属 | 机制与扩展点 |
|---|---|---|---|
| 空闲 / 走路 / 慢跑 / 奔跑 | **移动分级**（连续量的一维映射） | Sim 只有 `Vel`；**View** 做分级 | 速度 → 动画参数（BlendTree）；扩展点 = **阈值参数**（不是状态） |
| 起步 / 停步 | **纯表现过渡** | **View** | Animator 过渡（或表现机的过渡态）。**Sim 侧对应的是加/减速度参数**（物理），不是状态 |
| 冲刺 / 喝药 / 交互 | **离散时序动作** | **Sim**（判定）+ View（表现） | 动作系统：单主动作槽 + `canBeInterruptedBy` + `tb_action_num`。扩展点 = **加表行**（`dash` / `item` / `interact` 都是 `category` 取值） |
| 眩晕（及一切"限时压制"） | **限时状态效果** | **Sim**（判定）+ View（表现） | **Buff/状态效果系统**（《自研框架设计方案》§660 已定案：时长/叠加/tick/互斥，联机判定住 Sim；属性加成走 §663 聚合管线）。扩展点 = **加 Buff 行** |

**判据（新增状态先分类，再落地）**：

```
它的值由连续量算出来吗？              → 移动分级（View，加阈值）
它有前摇/持续/后摇、会被打断、要判定吗？ → 动作系统（Sim，加表行）
它是外部施加、有时长、期间压制别的行为吗？→ 状态效果（Sim 判定 + View 图标）
它只是"A 到 B 的动画过渡"吗？           → View 过渡（不进 Sim）
```

**⚠ 两条纪律**：
1. **"表现看起来对" ≠ "判定对"**：冲刺位移、喝药是否成功、交互是否完成、眩晕时长——**必须住 Sim**（服务器权威 + 回滚一致），不能只在表现层做迁移。
2. **不要一上来就加状态机状态**：加错层的两种后果——① Sim 被表现态污染（快照膨胀、回滚不一致）② 表现层承担判定（作弊面）。

### 2.5 真正的难点：三轴**不正交**（优先级与压制）

这 10 个状态不是平铺的，它们的关系是**三轴 + 压制**：

```
轴 1 移动分级（idle/walk/jog/run）        ← 连续
轴 2 离散动作（dash/drink/interact）      ← 单槽 + 中断规则
轴 3 状态效果（stun；将来 root/silence/slow/slow-move）  ← 限时叠加
────────────────────────────────────────────────────
轴 3 压制 轴 1 与 轴 2（眩晕时不能走、不能喝药）
轴 2 与轴 1 互斥（喝药可能禁步；交互读条"移动即取消"）—— 由中断规则表达
```
→ 所以问题的实质是**优先级仲裁**，不是"状态数量"。而**框架 HSM 明确不做并行状态**（《层级状态机施工图》§6）→ 正交轴**不可以用一条 HSM 的父子结构硬套**。

#### 三种落地形态（按复杂度递增）

| 形态 | 做法 | 何时选 |
|---|---|---|
| **A. 分离式（推荐起步）** | Sim：`Vel` + `ActionState`（单槽）+ 状态效果位；View：Base Layer 分级 + Override Layer 动作 + 状态效果表现（图标/特效） | 常规需求；**零新机制**——新增状态 = 加表行/阈值/Buff 行 |
| **B. View 侧"表现状态机 + 优先级 + 压制恢复"** | 一条 HSM 表达 10 个**表现态**：顶层 `Normal(子态: Idle/Walk/Jog/Run/Dash/Drink/Interact) / Stunned`；`Stunned` 压制任何子态，退出时**回到压制前的子态** | 表现逻辑复杂到需要**可测/可查/可调试**的状态（多段技能演出、状态互斥规则多） |
| **C. 一条大状态机塞全部** | — | ❌ **不做**：并行/压制表达不了，且会把 Sim/View 分层击穿 |

**B 形态的关键**：`Stunned` 退出要"回到之前的状态"——这正是 **HSM `HistoryMode.Shallow` 的真实用途**（顶层复合态 `Normal` 记住退出时的直接子态）。
（对照：《UI扩展能力设计》§1.5 里转场**不需要** HSM——那里的阶段是平的、无压制恢复；**角色表现机则确实需要**。同一框架能力，需求方不同，判据是"有没有压制-恢复"。）

### 2.6 与既有件的接口

| 既有件 | 角色 |
|---|---|
| `EntitySlot.Pos/Vel/Yaw` | 移动学与朝向（已有） |
| `MovementSystem` | 每帧积分（已有；动作对移动的接管是**输入层**的事，不改积分） |
| `ShootingSystem` | 消费朝向/瞄准做 hitscan（已有） |
| `SimCommand` / `SimFrameEvent` | 动作判定的输出（伤害/死亡通知；类型位已冻结，动作相关如需新类型走"预留位"流程） |
| `SimChecksum` | 覆盖 `ActionState`（它进槽位后自动纳入；若放 `CustomData` 需确认已在校验范围） |

## 3. View 侧：表现机（可选）与正交轴合成

### 3.1 正交轴的合成（关键）

"移动"与"战斗"**正交**（可以边走边开火），而框架 HSM **不做并行状态**（《层级状态机施工图》§6）→ 三条正解，**按需选**：

| 方案 | 形态 | 适用 |
|---|---|---|
| **A. 纯 Animator（推荐起步）** | Base Layer = locomotion（1D BlendTree 吃速度），Upper-body Override Layer = 战斗（吃 `ActionState.Phase`） | 表现需求常规；**零自研代码**，且这正是 Unity 的标准做法 |
| **B. 两条独立平面机 + 薄合成器** | `LocomotionMachine`（idle/run/sprint/air）+ `CombatMachine`（idle/aim/fire/reload/dead），合成器读两者阶段决定层权重 | 表现逻辑复杂（如"死亡时打断所有层""冲刺影响上半身"）；需要可测的表现状态 |
| **C. 一条 HSM** | 把战斗当"移动的子态"或反之 | ❌ **不做**——两者不是父子关系，硬套会产生"边走边开火"表达不了的结构 |

**纪律**：无论哪种，**表现不携带判定**；回滚重放期间必须 `silenceUntilFrame` 防重播（动画/特效/音效/震屏一视同仁）。

### 3.2 View 表现机形态（选 B 时）

> **多状态 + 压制**的场景（如 §2.4/§2.5 的 10 个状态）用 **HSM**（`HierarchicalStageMachine<TId,TReq>`）+ `HistoryMode.Shallow` 表达"压制结束后回到之前状态"；单轴、无压制的场景用**平面机**即可。

```csharp
// LiteGame / LiteSim.View 侧：订阅 Sim 帧事件，只做表现
enum CombatView { Idle, Aim, Fire, Reload, Dead }              // 平铺够用（不需要 HSM）
readonly struct CombatViewReq { /* 帧事件载荷：kind/entityId/value */ }

var m = new StageMachine<CombatView, CombatViewReq>("View.Combat",
    (CombatView.Idle, new IdleStage()), (CombatView.Fire, new FireStage()), /* ... */);

// 推进：Subscribe<FrameEvent> → m.Request(下一表现态) → Tick 帧末应用 → 阶段 OnEnter 播动画/特效
```
- **平面机**（不是 HSM）：这里的"层级"交给 Animator Layer 更合适。
- 迁移条件来自**帧事件 + 快照派生量**（如 `Hp == 0` → Dead），不来自"重新模拟"。

### 3.3 战斗移动 vs 平常移动（姿态 / Stance）——2026-09-17 补

**现成样板**：`Assets/Animator/Kazuko.controller` 已经是 **`Idle / NormalLocomotion / CombatLocomotion` + 各方向 Start/Stop 走跑 + L90/R90/L180/R180 转向 + BlendTree**（《联机Demo美术资源清单》§91）——用户前面问的"起步/停步"也在这套里（Start/Stop 剪辑）。**要定的是"它怎么被驱动"，不是重建动画结构**。

#### 第一步：分清差异范围（决定代价）

| | 差异范围 | 方案 | Sim 影响 |
|---|---|---|---|
| **① 只上半身不同**（瞄准/持枪/开火/换弹） | 上半身 | **Layer + AvatarMask**：Base Layer 一套移动 + 上半身 Override Layer | **零** |
| **② 全身姿态不同**（Run 与 Run_Combat 连腿都不一样） | 全身 | **两套 BlendTree + 姿态参数**（`Kazuko.controller` 就是这个形态） | 看它是否影响判定（见第二步） |

#### 第二步：**唯一的设计决策 —— 姿态是"表现参数"还是"玩法状态"？**

判据只有一条：**它影响判定吗？**

| 姿态影响什么 | 归属 | 载体 |
|---|---|---|
| 只改动画集（速度/位移/命中都不变） | **纯 View** | Animator 参数（由"是否瞄准/是否开火/武器状态"推导），**不进快照** |
| 改**移速倍率 / 可否冲刺 / 可否开火 / 命中相关** | **必须进 Sim** | `EntitySlot.Flags` 位（已有 `uint`）或 `CustomData`；**由已进 Sim 的权威数据推导**（武器 id / 装备槽） |
| 改朝向语义（自由移动 vs 锁定侧步） | 本项目**天然自由**（见第三步） | 无需 Sim 状态 |

**⚠ 方向纪律（极易搞反）**：姿态若进 Sim，必须 **权威数据 → 推导 Stance → 表现消费**（单向）。
反例：View 检测"玩家按住右键瞄准"→ 直接给 Sim 设 Stance —— 那是**输入**，应走 `InputFrame.Buttons`（已进 Sim）✓ 而不是让表现层反写权威态。

#### 第三步：本项目的特殊性 —— 俯视角**天然消掉一半问题**

- 《联机Demo设计》§13 已定案：**固定俯角跟随 + 自由瞄准（朝向与相机解耦）** → 角色朝向永远跟瞄准，移动方向自由 → **传统 TPS 的"非战斗走 / 战斗侧步"两套移动语义在这里根本不存在**（全程都是"边跑边射"的侧步式）。
- 所以差异**主要落在上半身**（瞄准/开火/换弹）→ **首推 ① Layer 方案**：一套移动动画（**资产不翻倍、过渡矩阵不翻倍**）。
- 只有美术明确要求"全身持枪跑姿 ≠ 空手跑姿"（正是 `Kazuko.controller` 的 Normal vs Combat）时，才上 ② 两套 BlendTree。

#### 第四步：Rig（**约束已解除**，2026-09-17 用户确认）

- **用户确认：`Erika Archer` 的 Rig 可以改为 Humanoid** → 原先"Erika=Generic 与 Kazuko=Humanoid 不可互换"的**硬前置消失**，动画方案选择不再受 Rig 限制（Retargeting 可用）。
- 因此"① Layer 一套移动 + 上半身覆盖"与"② 两套全身移动集"**都可行**，选择完全按**美术表达力**定：上下半身拆得开就 ①，全身姿态必须不同就 ②。
- 资产现状仍要处理：`Erika`（31 个射击动画，含 aiming idle/gunplay）**无 AnimatorController，需自建**；`Kazuko.controller`（两套 locomotion + 转向）现成可作参考实现/占位。
- 建议路径：**Erika 转 Humanoid → 自建 Controller（复用 Kazuko.controller 的结构做模板）→ 两套移动集按需要拆**。

#### 第五步：驱动形态（纪律：Animator 参数**单向驱动**，见《动效设计方案》§1）

```
〔Sim 权威数据〕速度 / 动作槽 / Hp / （若进 Sim 的）Stance
        │  单向
        ▼
〔View 推导〕Speed(float) / ActionPlaying(bool) / Dead(bool) / Aiming(bool) / Stance(bool)
        │
        ▼
〔Animator〕Base Layer：Speed → BlendTree（①一套 / ②两套按 Stance 选）
            Override Layer（上半身）：Aiming / Fire / Reload
            过渡：Start/Stop 等过渡剪辑由 Animator 自己管（表现过渡不进 Sim）
```
- **输入意图是合法的姿态来源**（"按住右键瞄准"→ `InputFrame.Buttons` → 已进 Sim → 再推导回表现）——但**始终单向**。
- 每帧写 Animator 参数要**值变才写**（与《UI性能优化规划》§7 的"值变才写"同族纪律）。
- 若姿态进 Sim：**回滚重放时 Animator 参数也会按重放结果回走** → 动画可能"倒带"→ 表现层需要 `silenceUntilFrame` 之外的处理（外插/钳制），这条列入 M11 表现验收。

### 4.2 五个关键设计点

**① 采样与逻辑帧对齐（渲染帧 ≠ 逻辑帧）**
- Input System 的输入是**事件驱动 + 轮询**；控制器在**每渲染帧刷新"待用意图"**，而 **Sim 只在逻辑帧边界消费一次**（`RollbackSim.Tick` 内每逻辑帧一次）。
- 一次渲染帧内跑多个逻辑帧（追帧 ≤5）时：**同一份意图被连续逻辑帧消费**（等价于"这一瞬间人没再操作"），不制造输入。
- **`InputDelay = 1`**（`SimConfig`）：本地输入延迟 1 帧提交，配合 `InputHistory` 与和解判定（既有设计，勿改）。
- **不做"每渲染帧一份输入"**：那会让逻辑帧数与输入数脱钩，回滚重放无法对齐。

**② 相机相关换算在 View（Sim 只收世界量）**
- WASD → **相机相对**方向 → 世界 `MoveX/MoveZ`（归一化到 ≤1）；鼠标 → 屏幕射线 → 地面交点 → `Aim`。
- Sim **不认识相机**（也不该认识）：它只吃"世界方向/朝向"。俯视角"朝向与相机解耦"由此成立（§14.3 的输入模型就是这一层的表述）。
- ⚑ **关键洞见（决定纪律边界）**：**输入是数据，不是计算**。换算里用 `Mathf.Atan2` 之类**不影响 Sim 确定性**——因为输入值被**记录（`InputHistory`）并传输**，重放走的是记录值而不是重算。所以 Sim 内那条"禁 `Mathf.*`"只约束 **Sim 内部计算**，不约束输入生成。

**③ 预测与回放（本地立即、远端插值）**
- 本地玩家的意图**直接进预测**（不等服务器）→ 操作 0 延迟感（M11 验收第 1 条）。
- 远端玩家输入由服务器转发，到达时 `OnRealInput` → 若与预测不符则回滚重放（既有 `RollbackSim`）。
- **重放必须用 `InputHistory` 的记录值**，绝不重算（这也是②成立的原因）。

**④ 键位重绑与双平台（`Input System` 的用武之地）**
- 工程**已引入 `com.unity.inputsystem 1.11.2`**（`Packages/manifest.json`），但代码里**还没用它**（现有仅 `SimSandbox`/DevHUD 用老 `Input.GetKey` 做调试）。
- 形态：**两张 Action Map**（`Gameplay` / `UI`）+ **一个意图面**（`IIntentSource`：`Move` / `Aim` / `Fire` / `Skill1..3`），两种实现：
  - **键鼠**：WASD + 鼠标瞄准 + 左键射击 + Q/E/R 技能
  - **触屏**：双摇杆（左移动/右瞄准）+ 技能按钮
  - → 与《联机Demo设计》"双平台同一输入模型 + 输入服务双实现"一致。
- **键位重绑**（M11 交付项）：Input System 自带 `PerformInteractiveRebinding`；绑定覆盖串存 `SettingService`（既有存储），启动期应用。
- 判据：**重绑/多设备/触屏**这三条是 Input System 的主场；老 Input Manager 要自研这些 → 直接用 Input System（已在工程，零新增依赖）。

**⑤ 输入两层校验（对齐 §4.5）**
- **传输层**（M10 已定）：频率限制 + `ackInput` 单调，挡非法/重放包。
- **Sim 内 clamp**（M11）：`Move` 模长 ≤1；非零 `Aim` 归一化；`Buttons` 白名单位（未定义位置 0）；帧号越界钳制。
- **为什么不靠服务器拒绝非法输入**：服务器拒绝 → 客户端已预测 → 分叉 → 和解风暴；**clamp 比拒绝便宜**（既有定案）。

### 4.3 输入上下文与优先级（易漏项）

| 上下文 | 输入行为 |
|---|---|
| 对局 | `Gameplay` map 生效 |
| UI / 菜单（全屏界面） | **切到 `UI` map**，战斗意图**置零**（不能"边开菜单边走"） |
| 死亡 / 观战 | `Gameplay` 关闭，只留观战操作（相机/切人） |
| 回放 | **不接真实输入**，由 `InputHistory`/归档喂 |

- 实现落在**壳层门**：`UIService` 已具备"全屏界面激活 → 更低层级组 Covered"的语义（既有），控制器据此把 `Gameplay` map 切掉即可——**不新增输入上下文服务**（判据：现有层级/遮盖语义已能表达"谁该吃输入"）。
- 判据留档：若出现"同一屏内 A 区域吃输入 B 区域不吃"这类**局部**需求，再引入输入上下文栈。

### 4.4 相机（引用既有定案，不重复设计）

`ICameraService` 住 `LiteSim.View`（**不进框架**）：跟**本地预测位置**（0 延迟）；和解期跟**已衰减的表现位置**（不 snap）；震屏 = Impulse + View 观察触发 + `silenceUntilFrame` 防重播；档位（俯角/距离/FOV/边界）由**模式策略包**提供；挂 `IWorldClock`（时停冻结）。验收五条见《联机Demo设计》§3.1。

### 4.5 两范式差异（控制器接口不变）

| | 状态同步（主路线） | 帧同步（预案） |
|---|---|---|
| 输入去向 | 上传服务器（Unreliable + 冗余 4 帧），服务器权威模拟 | 输入中继给所有客户端，全员本地模拟 |
| 本地表现 | 预测 + 和解 | 直接模拟（无和解） |
| 输入记录 | `InputHistory` 32 帧（重连补发 + 回滚） | 同样需要（回滚/重放） |

**控制器的接口与数据形态完全一致**（都产出 `SimInputFrame` 并记录），差异只在 `INetworkService` 的实现（"输入从哪来/去哪"）——这是"两范式同构"在控制层的体现。

### 4.6 重连 / 回放 / 观战

- **重连**：`InputHistory` 32 帧为补发留余量（既有）；重连后由服务器给基线快照 + 输入补发。
- **回放/归档**：`MatchArchive`（种子 + 输入流）→ 回放时喂记录输入，**不接设备**；表现层照走，但不得触发"玩家操作反馈"（如震屏/UI 提示）。
- **观战**：不产生输入；相机走观战档位。

## 8. 不做（判据留档）

| 不做 | 判据 |
|---|---|
| Sim 侧用框架状态机 | 红线（`references: []`）+ 快照约束（对象图不可 CopyTo）——**没有判据可翻** |
| 给移动做状态机 | 连续映射，无迁移条件；出现"移动本身有前摇/硬直"（如起跳不可取消）时，把它归到**动作槽**而不是移动状态机 |
| 并行状态（正交轴用一条机表达） | HSM 不做并行；正交轴用 Animator Layer 或两条机器 |
| 输入上下文栈 / 独立的输入服务 | 现有层级+遮盖语义够用；出现"局部区域吃输入"再引 |
| 服务端拒绝非法输入（替代 clamp） | 会引发预测分叉与和解风暴（既有定案：clamp 优于拒绝） |
| 回放期触发玩家操作反馈（震屏/UI 提示） | 回放不是操作；`silenceUntilFrame` + 回放标记门 |

## 9. 定型方案（Final，2026-09-17 —— 拍死，不再列选项）

> 前置已定：瞄准用 `Aim` 方向（§7-1）；Erika 可转 Humanoid（§3.3 第四步）；Sim 不引用框架（红线）；框架状态机可用于 View。

### 9.1 Sim 侧数据模型（字段级定型）

```csharp
// ① 输入（每逻辑帧一份；已定 Aim 方向）
struct SimInputFrame { long EntityId; float MoveX, MoveZ, AimX, AimZ; uint Buttons; }
// Buttons 位（白名单，未定义位必须为 0）：Fire | Aim | Dash | Skill1 | Skill2 | Skill3 | Interact | Use

// ② 实体槽（在既有 EntitySlot 上**追加**一个字段）
struct EntitySlot {
    long Id; SimVector3 Pos, Vel; float Yaw; int Hp; uint Flags;   // 既有（Yaw 降为派生）
    ActionState Action;                                            // ★ 新增：单主动作槽
}
struct ActionState { int ActionId; int StartFrame; ActionPhase Phase; long SourceId; }

// ③ 状态效果（眩晕等）→ 落既有 CustomData[32]，每实体 4 槽 × 8B（单一真相，不用 Flags 位）
//    槽 = { ushort EffectId; int EndFrame; ushort Param; }   ← Param 承载"减速 30%"这类参数
//    分配属主：CharacterStateSystem（写进本文与 §2.6 接口表；CustomData 已在 SimChecksum 覆盖范围内）
```

**三条字段纪律**：
1. **单一真相**：状态效果只住状态槽，**不用 `Flags` 做状态位**（两份真相必然漂移；`Flags` 留给"每帧重算的布尔缓存"）。
2. **不加 `Stance` 字段**：姿态由 `Buttons.Aim` + 动作槽**推导**（见 9.2）；将来真出现"拔刀/收刀"这类**玩家显式姿态切换**且影响判定时，再加 `Flags` 位。
3. **加字段即改 checksum**：`SimChecksum` 是硬编码逐字段 Mix——给 `EntitySlot` 加字段必须同步遍历（漏掉 = 校验漏字段，回滚比对会漏报）。

### 9.2 判定归属表（复杂状态逐个拍死）

| 状态 | Sim 归属 | Sim 载体 | View 表现 |
|---|---|---|---|
| 空闲/走路/慢跑/奔跑 | 只有 `Vel` | — | `Speed` → BlendTree（阈值参数化） |
| **起步/停步** | 加/减速度参数 | `MovementSystem` 参数 | Animator Start/Stop 过渡（**不进仲裁**） |
| **冲刺** | 动作 | `ActionSlot(actionId=dash)` | 动画 + 位移由 Sim 算 |
| **喝药** | 动作 | `ActionSlot(item)` + 效果结算 | 动画 + 进度条 |
| **交互** | 动作 | `ActionSlot(interact)` | 读条 UI |
| **眩晕** | 状态效果 | `StatusSlot(stun, endFrame)` | 头顶图标 + 受击动画 |
| **瞄准/开火** | 输入位 | `Buttons.Aim / Fire` | 上半身 Override Layer |
| **战斗/平常移动（姿态）** | **不落字段**：判定侧读 `Buttons.Aim` + 动作槽推导（用于移速倍率/禁冲刺） | 推导量 | `Stance(bool)` → 移动动画集选择 |
| 死亡 | 既有（`Hp<=0` + CleanupSystem） | 槽位 | 死亡动画 + 停止输入 |

### 9.3 仲裁优先级（唯一权威顺序）

```
P0 死亡          ← 压制一切（输入置零、清动作槽、清移动）
P1 状态效果      ← 眩晕/击飞：压制移动与动作（Sim 侧查 StatusSlot）
P2 动作槽        ← 冲刺/喝药/交互：压制移动分级；按 canBeInterruptedBy 决定能否被抢槽
P3 移动分级      ← idle/walk/jog/run：受 P2 的"禁步"规则约束
P4 表现过渡      ← 起步/停步：P3 内部的平滑，**由 Animator 过渡承担，不参与仲裁**
```
**仲裁在 Sim 侧是"数据+表的合成"，在 View 侧是"Animator 层的权重"** —— 两处都不需要状态机。

### 9.4 View 侧定型：默认**不引入**表现状态机

**理由**：Animator **本身就是状态机**；再叠一层 = 同一份状态拆两处维护（"重复机制"）。

#### 触发判据：**三合一，缺一不上**

```
① 非权威   —— 该表现态**不能**从 Sim 权威数据直接推导出来
② 被读取   —— 别的逻辑要"问"当前是什么表现态（不只是被写）
③ 抢占/分支 —— 存在抢占-恢复语义，或运行时条件决定分支
```

**⚠ 一处修正（2026-09-17，本文件先前说得太宽）**：早先把"眩晕结束回到之前状态"当作 HSM `HistoryMode.Shallow` 的典型需求方 —— **多数情况下不需要**。因为"之前的状态"（移动/动作槽）本就是 **Sim 权威态** → 恢复由 **Sim 决定**（状态效果槽 + 动作槽），View 只需单向跟随。**View 侧历史只在"被抢占的表现态本身不是权威态"时才需要**（相机模式、界面内演出、引导进度这类）。

#### 具体场景对照（本项目）

| 场景 | 真需要 View 状态机？ | 替代/正解 |
|---|---|---|
| 死亡动画播完才回收 / 弹结算 | ❌ 不需要 | Animator 事件回调（或状态机行为）+ 读 Sim `Hp`；必要时 UniTask 延时 |
| 技能演出期间禁用 UI/输入 | ❌ 不需要 | **读 Sim 动作槽**（权威）+ `silenceUntilFrame` |
| 眩晕结束"回到之前状态" | ❌ 多数不需要 | **Sim 侧**状态效果槽 + 动作槽决定恢复（见上方修正） |
| 连续受击不叠加抖动 | ⚠️ 大概率不需要 | Animator 自身过渡 + 一个"最近受击帧"时间戳 |
| 三段斩"目标已死则改路线" | ⚠️ 可选 | 条件表 + Timeline 分支；状态机非必需 |
| **相机模式切换**（俯视角 ⇄ 观战 ⇄ 回放）被战斗 UI 抢占再恢复 | ✅ **典型需求** | 非权威态 + 被读取 + 抢占恢复 —— 三合一全中 |
| **界面内多段演出**（结算页 统计→翻牌→奖励→确认，可跳过/中断） | ✅ 可能 | 规模小就 UniTask 序列 + 打断标记；多且有分支才上 HSM |
| **引导序列**（多步、可打断、要记进度） | ✅ 可能 | 但引导有自己的**解释器**（内容层归属，见设计方案 §4.4），不走角色表现机 |

#### 落地态度

**先把 A 方案（Animator + 参数单向驱动）跑起来**；M11 遇到第一个疑似场景时用上面三条件过一遍 —— **大概率不需要**。真需要时用 `HierarchicalStageMachine` + `HistoryMode.Shallow`（此时"历史"记的是**非权威表现态**，与 Sim 权威态无冲突）。

### 9.5 三条纪律（不再重复讨论）

1. **单向数据流**：`Sim 权威 → 推导 → 表现`；表现层**永不反写**权威态（输入是唯一的反向通道，且它走 `InputFrame`）。
2. **判定与表现分离**：影响判定的状态（移速/可否冲刺/命中/时长）**必须住 Sim**；"看起来对"不算对。
3. **值变才写**：写 Animator 参数/控件同样只写变化（与《UI性能优化规划》§7 同族）。
4. **回滚重放的"倒带"要处理**：姿态/动作进 Sim 时，重放会让 Animator 参数回走 → 表现层需外插/钳制（不能只靠 `silenceUntilFrame`）。
