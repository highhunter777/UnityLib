# 金华 JP 手游项目架构解析

> 本文档汇总对 `c:/jinhuaJP/Assets`(Unity 手游工程)的逐项解析,涵盖目录划分、业务模块、动态资源、技能数据、事件总线与协议总线。
>
> 技术特征:HybridCLR 热更新 + Addressables 远程资源 + 微信/快手小游戏 WASM SDK + Spine 动画 + Luban 配置表。游戏类型为**二次元卡牌 / RPG**(含英雄养成、抽卡、战斗、社交、海量运营活动)。

---

## 0. 关键架构特征速览

- **热更新双程序集**:`Framework`(AOT 主包基础)+ `Hotfix`(HybridCLR 动态加载,运行时代码不进主包),`smcs.rsp` 为编译指令。
- **资源三级**:`Resources`(内嵌)→ `StreamingAssets`(随包)→ `DynamicRes`(远程 CDN 下载)。
- **多端适配**:同时含微信(`WX-WASM-SDK-V2`)/ 快手(`KS-WASM-SDK-V2`)小游戏 WASM SDK + `Plugins/Android`/`iOS`。
- **双总线**:进程内跨模块用**事件总线**(`EventManager`),客户端↔服务器用**协议总线**(`NetMessageManager`)。
- **底层框架来源**:网络栈为 ET(Egametang)框架风格改造(`NetEntity`/`ComponentFactory`/`ProtobufPacker` 等);事件总线源码头标注源自「第七史诗」模板。

### 动态资源设计要点
- **热更闭环**:`ReleaseAssembly/Hotfix_dll.bytes`(代码) + `Tables/`(配置) + `UI/`(界面)三者共同构成可远程更新的热更包,不需发版即可改玩法/数值/界面。
- **类型→目录映射**:代码模块(`Hotfix/Features/Xxx`)与资源(`DynamicRes/UI/Xxx`)按同名子目录对齐,便于 Addressables 按 label 分组加载。
- **`Inner/` 兜底**:关键 Prefab/Texture 放包内,防止首包下载失败白屏。
- **图集策略**:通用走自动图集(`UI/` 内),主城等高频界面用手动图集(`UIManualAtlas/`)控制 DrawCall。

## 4. SkillData 文件夹解读(`DynamicRes/Data/SkillData/`)

**战斗技能「演出/表现」数据目录**——由技能编辑器导出,描述一个技能在战斗里**怎么演**(动画、位移、特效、音效、镜头的时间轴),**不含伤害数值**。数值来自服务器 protobuf(`pbSkill`),两者在战斗运行时合并。

### 4.1 单个技能文件(`<技能ID>.json`)
约上千个,文件名即技能 ID。结构:
```json
{
  "name": "风龙【0】",        // 技能名
  "id": 1102010,              // 技能ID(前缀=英雄ID 110201)
  "actorId": 110201,          // 施法英雄
  "wraithId": 0,              // 缚灵ID(缚灵技用,特效取此、模型取actorId)
  "zwSolution": 1, "targetNum": 1,
  "movementData": {           // ★ 核心时间轴
    "atk_type": 1,            // 攻击类型(1普通/3/5…)
    "skillUsefulCamp_type": 1,// 作用阵营
    "skillTargetChoice_type": 1, // 选敌方式
    "totalTime": 2.2,         // 技能总时长(秒)
    "skillHasMask"/"maskStopTime", // 遮罩
    "skillShowHideHp"/"skillUIShowHide", // 演出时血条/UI显隐
    "events": [               // 事件序列,按 startTime 触发
      { "clipName":"skill_0", "actorType":1, "startTime":0.0,
        "moveTargetType":1, "moveTime":0.1, "posFromX/Y","posToX/Y",
        "curePosX/Y":{AnimationCurve}, ... },  // ActorAniEvent 位移+动画
      { "clipName":"hit", "actorType":2, "startTime":0.5 } // 受击帧
    ]
  }
}
```
事件类型(`events[]`):`ActorAniEvent`(播 Spine 动画+位移,带 AnimationCurve 曲线)、`PlayEffectEvent`(挂点特效,nodeName: root/ef_1/pao1…)、`AudioEvent`(音效)、`CameraEffectEvent`(震屏/聚焦)、`DamageResultEvent`(结算点,通常由代码自动补)。

### 4.2 `Set/set.json` — 资源依赖清单(自动化生成)
打包/Addressables 用。每行一条:
```
90504,5,1,3,effect:SkillTemp/90504/skill_1;...skill_1_hit|sound:90504|actorNode:origin
```
即 `id, atk_type, camp, targetChoice, effect:特效路径 | sound:音效 | actorNode:挂点`。构建时据此收集每个技能依赖的特效/音效 prefab,保证资源分组正确(`GStore.BattleSkill.SkillData.SaveSetJsonData` 生成)。

### 4.3 `SkillUIOffset/offset.json` — UI 偏移表
`{"Id":英雄ID, "Content":"x,y"}`,战斗中技能名/图标相对英雄的屏幕偏移,用于把演出 UI 对齐到角色。

### 4.4 两套 C# 模型
- **`Framework/GStore/BattleSkill/SkillData.cs`**(框架/数据侧):`SkillData`/`SkillMovementData` 模型,`Deserialize`(SimpleJSON 读 JSON)、`ReadData`、`SaveSetJsonData`(生成依赖清单)、特效路径拼接 `Assets/DynamicRes/Prefabs/Effect/`。
- **`Hotfix/.../Battle/BattleSkill/Base/BattleSkillData.cs`**(战斗运行时):`BattleSkillData.Deserialize(Skill pbSkill, heroUnit…)` 是**核心合并逻辑**:
  1. `pbSkill`(服务器 protobuf,含 `Effect`/`Buff`/`Combos`/`Source`)经 `GetSkillShowSet` 映射 → `LoadSkillTextAsset(skillSetId)` 读本地时间轴 → 转成 `SkillEvents`;
  2. 数值按 Combo 分组 → `SkillEffects`(每击伤害/buff/目标)、`ShelterEffects`(庇护站位)、`SkillEffectTargetIds`;
  3. 自动校准 `DamageResultEvent`(以 `hit` 动画/特效名 `_end`/`sin` 推断结算时刻),并补 `FocusEvent`(镜头聚焦)、`ShelterEvent`;
  4. 标记 `IsBgSkill`(大招/缚灵)、`HasCameraShake/Focus`、来源(0英雄/1主角/2暗器/3羁绊/4领域/5式神)。

### 4.5 ID 命名规律
- 技能 ID 高几位 = 英雄 ID(`1102010`→英雄 `110201`,与 `Animations/835002_skill_1.anim`、`DynamicRes/UI` 命名一致)。
- 前缀分布:`11xxxx`、`34~46xxxx`=英雄技能;`81~85xxxx`=暗器/召唤;`90xxx`/`903xxx`/`905xxx`/`906xxx`=领域/通用 buff(如 `LingyuBuff` 灵域)。

> **一句话**:SkillData 是「技能演出剧本」(本地 JSON 时间轴),数值由服务器下发,运行时通过 `skillSetId` 把剧本与数值合成 `BattleSkillData` 驱动整场战斗表现。

## 5. Features 功能目录详解(`Scripts/Hotfix/Features/`)

热更层全部业务功能的容器(69 个子模块 + 顶层散文件),是游戏的「玩法逻辑中枢」。

### 5.1 模块统一约定(核心机制)
每个功能 = 一个继承 `Core.Feature` 的类(`Core/Feature.cs`):
```csharp
public abstract class Feature {
    public abstract void Init();              // 数据初始化
    public virtual  Task LoginReq();          // 登录时拉初始数据
    public abstract void Clear();             // 清理
    protected void BindEvent(EEvent, handler);// 绑事件总线(自动追踪,回收时解绑)
    protected void RegisterProtocol<T>(action);// 绑网络协议(自动解注)
}
```
特性标记:`[Feature]` 或 `[Feature(sort)]`(`Manager.cs` 里 `FeatureAttribute` 带 `Sort` 排序值)。

**要点**:模块只声明「要监听什么事件/协议」,生命周期与清理由基类 `Recycle()`(`Clear` + `EventTracer.Dispose` + `UnRegisterAllProtocols`)集中托管,避免泄漏。

### 5.2 总控 `Features/Manager.cs`(单例 + `IUpdate`)
- 反射 `AttributeHelper.GetHotfixTypesByAttribute<FeatureAttribute>()` **自动发现**所有 `[Feature]` 类 → `Activator.CreateInstance` 实例化。
- 按 `Sort` 分组(`SortedDictionary`)→ 登录时**并发 8 路**(`LoginReqConcurrency = 8`)调各模块 `LoginReq()`,并记录 `LoginTimeoutFeature`(超时定位)。
- 持有 `Dictionary<Type, Feature> datas`,对外 `Get<T>()` 取模块实例(如 `Manager.Instance.Get<Player>()`)。

### 5.3 目录布局
- **顶层散文件**(无子目录的「单文件功能」):`Manager.cs`(总控)、`Activity.cs`(`[Feature(100)]` 运营活动聚合)、`Player.cs`、`Login.cs`、`ServerTime.cs`、`Storage.cs`、`Sound.cs`、`Tasks.cs`、`Recharge.cs`、`RoleResource.cs`、`Sociality.cs`、`PersonalSpace.cs`、`BattleVideo.cs`、`GhoulRoad.cs`、`Guide.cs`。
- **69 个子模块目录**(见第 2 节分类)。

### 5.4 典型模块内部结构(命名约定)
以 `Summon/` 为例:`Summon.cs`(Feature 逻辑) + `SummonData.cs`(数据) + `SummonDefine.cs`(枚举/常量)。通用约定:

| 后缀 | 含义 |
|------|------|
| `X.cs` | Feature 子类(主逻辑) |
| `XData.cs` | 数据持有者 |
| `XDefine.cs` / `Define.cs` | 枚举/常量(常置于 `Features.Define.*` 命名空间) |
| `XHelper.cs` | 静态工具方法 |

复杂模块再拆子目录(见 `Battle`、`League`、`Hero` 等)。

### 5.5 三大重量级模块
**1. `Battle/`(93 文件)— 战斗引擎**
`BattleControl.cs`(总控)、`BattleActor/`(战斗实体)、`BattleSkill/`(★ 即第 4 节分析的技能演出,`Base/BattleSkillData.cs`)、`BattleCameraMgr`/`BattleAssetMgr`/`BattleNetWork`/`BattleFormula`(数值公式)、`RoundAtion/`(回合行动)、`HangUpShow/`(挂机表现)、`BattleUI.cs`、`BattleProgressBar/`、`Interface/`、`Net/`、`Tool/`、`UIRefreshTool`。

**2. `Activities/`(244 文件)— 运营活动框架(数据驱动)**
不是 244 个手写活动,而是一套**通用活动系统**:
- `Promotion.cs` — 单个活动模型(含 `Service`/`Duty`/`Module`/开放状态/图标/排序/视图类型)。
- `EPromotion.cs`(活动 ID 枚举)、`EType.cs`(活动大类)、`Module.cs`、`PromotionAttribute.cs`。
- `Modules/`(110 文件,按玩法分组):`AFK`(挂机) `Fixtures`(75,装置/家具) `Market`(集市) `Misc` `Relics`(遗迹) `Skin`(皮肤) `Special` `Tower`(爬塔)。
- `Services/` — 与 `Modules` 平行的数据/网络服务(AFK/Fixtures/.../Wraith)。
- `Duties/` — `Disposable.cs`/`Periodic.cs`(活动内周期任务,如每日重置)。
- 顶层 `Activity.cs` 聚合所有 `Promotion`,按 `EFunc`/`EPromotion`/`EType` 建索引,订阅红点 + 全局事件(功能开启/跨天/充值/升级…)与协议。**新增活动 = 加枚举 + 实现 Module/Service,配置走 Luban 表。**

**3. 养成类(多子目录)** `Hero/`(9:`HeroData`/`HeroFetter`/`ExclusiveWeapon`/`Totem`…)、`Equip/`(7)、`Formation/`(6:`SingleFormationData` 等)、`League/`(9:`LeagueWar`/`LeagueMatrix`/`LeagueFantasyLand`…)、`Wraith/`(9)。

### 5.6 与其它层的关联
- **↔ UI 层**:Feature 逻辑里直接引用 `UI.Controllers.*` — Feature 管状态/数据,Controller/View 管表现(上一轮 `Hotfix/UI` 的 106 模块)。
- **↔ 数据层**:通过 `Database`(Luban 生成的 `AutoGen`/`LubanMaual`)读配置表;数值模型写在 `PBStruct`(服务器协议)。
- **↔ 功能开启**:广泛引用 `Features.Define.OpenStatus`(功能解锁条件门控,由 `OpenStatus` 模块维护)。
- **↔ 红点**:`Activity`/`Feature` 普遍 `SubscribeRedDot` / 触发红点事件。

> **一句话**:Features 是「按功能纵向切分、由 `Manager` 反射统一编排」的热更业务层——每个 `Feature` 自管数据/事件/协议,重量级模块(Battle/Activities/养成)再横向拆分;运营活动走 Activities 数据驱动框架,数值来自服务器、配置来自 Luban。

## 6. 事件总线(EventManager)

项目事件总线位于 `Hotfix/Core/Event/`,是整个热更层**跨模块解耦通信**的核心。

### 6.1 文件地图
| 文件 | 角色 |
|------|------|
| `Common/EEvent.cs` | 事件标识枚举(**417 项**),按 `#region` 按领域分组 |
| `Core/Event/GameEventArgs.cs` | 事件载荷基类 + 常用子类(全部接入引用池) |
| `Core/Event/EventPool.cs` | **真正的引擎**:订阅表 + 事件队列 + 派发 |
| `Core/Event/EventManager.cs` | 门面(`GameManager.GEventManager`),实现 `IManager`+`IUpdate` |
| `Core/Event/EventTracer.cs` | **生命周期守卫**,被 `Feature` 使用,确保订阅可干净回收 |

### 6.2 事件标识 `EEvent`(417 个枚举值)
`Hotfix/Common/EEvent.cs`,按业务域用 `#region` 分段:`E_NULL`、`E_ENTRY_LOADING`、`E_FEATURE_OPEN`、`E_UI_OPEN/CLOSE`、声音、`角色`(E_ROLE_UPDATE_LEVEL…)、`英雄皮肤`、`脉冲`、`斗魂`、`元素之力`、`神话余韵`… 每个枚举值 = 一条独立的事件通道。

### 6.3 事件载荷 `GameEventArgs`(引用池化,零 GC)
抽象基类实现 `IReference`,带 `EventType` 字段。常用子类:
- `DefaultEventArgs` — 无参(`DefaultEventArgs.Create(eEvent)`)
- `CommonEventArgs` — `object[] Args` 可变参
- `CommonOneEventArgs<T>` — 单类型参
- `JumpEventArgs`(`JSONNode`)、`TabEventArgs`(tab 索引)
- 全部通过 `ReferencePool.Alloc<T>()` 取、`Release()` 还,**避免事件频繁触发造成 GC**。

### 6.4 核心引擎 `EventPool<T>`
```csharp
Dictionary<EEvent, EventHandler<T>> m_EventHandlers; // 每事件一个多播委托(+= 订阅)
Queue<Event> m_Events;                               // 待派发队列
HashSet<EEvent> reduceSet;                           // 同帧去重集
EventHandler<T> m_DefaultHandler;                    // 兜底处理器
```
关键点:
- **多播**:`Subscribe` 用 `+=` 把 handler 接到该事件的委托上,一个事件可被多个模块监听。
- **Fire(异步)**:`lock` 入队;若载荷是 `DefaultEventArgs` 且本帧该类型已入队 → **跳过重复**(`reduceSet`),实现「同帧合并刷新」(如多次 `E_RESOURCE_UPDATE` 只刷一次)。
- **FireNow(同步)**:`HandleEvent` 立即 `Invoke`,不经队列。
- **派发**:`HandleEvent` 取订阅者 `Invoke`;无订阅者则走 `m_DefaultHandler`(兜底);派发后 `ReferencePool.Release(e)` 回收载荷。
- `Event` 内部节点自身也是 `IReference` 池化对象。

### 6.5 门面 `EventManager`(`GameManager.GEventManager`)
- `Fire(eEvent, e, sender)` —— **延迟派发**(入队,下一帧 `Update` 处理,线程安全)。
- `FireNow(eEvent, e, sender)` —— **立即派发**。
- `Subscribe/Unsubscribe/Check/Count`、`SetDefaultHandler`。
- `Update()` 每帧 `m_EventPool.Update()` 排空队列。

> `Fire` vs `FireNow`:跨模块通知(可等一帧)用 `Fire`;需要同步拿到结果(如渲染前立刻重建 UI)用 `FireNow`。

### 6.6 生命周期守卫 `EventTracer`(关键!)
`Core.Feature` 里 `BindEvent` 实际走 `EventTracer`:
- `Bind(evt, handler)` → 调 `GEventManager.Subscribe`,并**双向记录**映射(`events`: evt→handlers、`handlers`: handler→evts),重复绑定会报错。
- `UnBind(evt)` / `UnBind(handler)` → 反向查表**精准退订**(不会误退他人)。
- `Pause()` / `Resume()` → 临时退订/恢复(模块挂起时保留记录)。
- `Dispose()` → 全部退订并清空。`Feature.Recycle()` 即调用它。

**这就解决了「在管理器里订阅了却忘了退订 → 切场景后空引用」的经典坑**:每个 Feature 只管 `Bind`,销毁时 `Recycle()` 自动连同 `EventTracer` 把该 Feature 的全部订阅一次性摘干净。

### 6.7 完整流转链路
```
Feature.Init()
  └─ BindEvent(E_XXX, OnXxx)  ──► EventTracer.Bind ──► GEventManager.Subscribe ──► EventPool[E_XXX] += OnXxx

某处触发:
  EventManager.Fire(E_XXX, args)        ← 入队(同帧 DefaultEventArgs 去重)
  或 EventManager.FireNow(E_XXX, args)  ← 立即 Invoke

每帧 Update():
  EventPool.Update → 出队 → HandleEvent → OnXxx(sender, args) 按序执行 → Release(args) 回池

Feature 销毁:
  Recycle → EventTracer.Dispose → 逐一 Unsubscribe → 订阅表清空(无悬空)
```

### 6.8 设计要点
1. **双模式派发**:`Fire`(异步/线程安全/帧去重)与 `FireNow`(同步),按需选择。
2. **多播 + 默认兜底**:一事件多订阅者;`m_DefaultHandler` 接住无人订阅的事件(调试/兜底)。
3. **引用池化**:事件节点与载荷均走 `ReferencePool`,移动端高频事件零 GC 压力。
4. **同帧合并**:无参事件同帧只派发一次,避免重复刷新(性能优化)。
5. **订阅/生命周期绑定**:`EventTracer` 让「订阅-回收」成对,杜绝内存泄漏与空引用。

## 7. 协议总线(NetMessageManager)

`NetMessageManager`(`Hotfix/Managers/Network/`)是**客户端↔服务器**的协议总线,相当于事件总线(`EventManager`)的「网络版」:事件总线是**进程内**跨模块通信,协议总线是**跨网络**通信。它是对底层 ECS 网络栈(`Framework/NetMessage/`,ET 框架风格的改造)的门面包裹。

### 7.1 两大用途
1. **推送(Push)**:服务器主动下发 → 客户端 `Register<T>(handler)` 订阅。
2. **请求/响应(RPC / NRPC)**:客户端 `CallRequest<T>(request)` 主动发并 `await` 返回。

### 7.2 协议标识:`protoId`(opcode)映射
由 `Hotfix/Utils/ProtobufHelper.cs` 管理:
- 每个 protobuf 消息类带 `[Message(Opcode = xxx)]` 特性(`PBStruct` 命名空间)。
- 启动时 `AutoRegisterProtocol()` 反射扫描全部 `[Message]` 类型 → 建 `type ↔ protoId` 字典。
- `GetProtoId<T>()` 取 id;`GetTypeByProtoId(id)` 反查类型。

### 7.3 订阅机制(推送,单播)
```csharp
public static void Register<T>(Action<T> action) where T : IMessage {
    var protoId = ProtobufHelper.GetProtoId<T>();
    _messageHandlerMap.Add(protoId, (bytes) => {
        var msg = ParseMessageFrom<T>(bytes);  // ByteString → T (Protobuf)
        action(msg);
    });
}
public static void UnRegister<T>() { ... _messageHandlerMap.Remove(protoId); }
```
- 存于 `_messageHandlerMap : Dictionary<int, Action<ByteString>>`。
- **单播**:每个协议由唯一 owner 注册(重复 `Add` 会抛异常),与事件总线的「多播」相反。`Feature.RegisterProtocol<T>` 即转调此处;销毁时 `Feature.Recycle → UnRegisterAllProtocols` 退订。

### 7.4 底层数据流(收包)
```
网络字节 → GameNetworkComponent(ProtobufPacker 解包)
  → GameMessageDispatcher.Dispatch → handler = MessageDispatch
    → MessageWrapper.Parser.ParseFrom(bytes)  // 得 ProtoId + Data(ByteString) + SerialNumber(rpcId)
    → 路由:
        SerialNumber == 0  → 推送 / NRPC响应
            ├─ _messageWrapperCallbacks[protoId] 存在 → 唤醒 NRPC 回调
            └─ 否则 → MessageHandler(protoId, Data) → _messageHandlerMap[protoId]?.Invoke  ← 推送落地
        SerialNumber != 0  → RPC响应
            ├─ _rpcRecivedIds.Add(rpcId)
            └─ _rpcWrapperCallbacks[rpcId] → tcs.SetResult(wrapper)  ← 唤醒 CallRequest 的 await
```
- `MessageHandler` 找不到 handler 会 `LOG.Net.E("Not found handler for protobuf id")`。
- `MessageDispatch` 里还做了请求耗时统计(`LogRequestCost`,打印 `[协议请求耗时]`)。

### 7.5 发送 / RPC
- `CallRequest<T>(request, isRPC=true)` → `SessionCall`:
  - 构造 `MessageWrapper{ ProtoId, Data = request.ToByteArray(), SerialNumber = rpcId }`。
  - `rpcId = isRPC ? ++Session.RpcId : 0`(RPC 用序号关联, NRPC 用 0)。
  - 把 `TaskCompletionSource` 存入 `_rpcWrapperCallbacks[rpcId]`(或 `_messageWrapperCallbacks[protoId]`)。
  - `Session.Send(wrap)`,返回 `tcs.Task` → `await` 拿到 wrapper 后 `ParseMessageFrom<T>`。
- **超时**:`UseSendTimeout`(默认 true),发后起 `Observable.Timer(8s)`,超时触发 `sessionErrorCallback(ERR_Timeout)`。
- **业务错误**:服务端不返回原类型而返回 `TipsMessage`(提示)→ 走提示处理,`CallRequest` 返回 `default(T)`。
- **断线重连** `OnReConnect()`:把 `_rpcWrapperCallbacks` 里未完成的请求重发。

### 7.6 连接管理
- `SetServerAddress` + `Connect` 建 `Session`;`Update()` 每帧 `NetEntity.Update()` 驱动网络轮询 + `HeartBeat` 心跳事件。
- **当前强制 `WebGLSocket`**(WebSocket),TCP 代码被注释 → 适配小游戏/WebGL(不支持 TCP socket),与项目含 WX/KS 小游戏 SDK 一致。

### 7.7 与事件总线对比
| | 事件总线 `EventManager` | 协议总线 `NetMessageManager` |
|---|---|---|
| 通信域 | 进程内(模块间) | 客户端↔服务器 |
| 标识 | `EEvent` 枚举(417 项) | `protoId`(opcode) |
| 订阅 | **多播**(`+=`,多模块监听) | **单播**(每协议一个 handler) |
| 触发 | `Fire`(帧延迟)/`FireNow`(同步) | 服务器下发 / `CallRequest`(await) |
| 载荷 | `GameEventArgs`(引用池) | protobuf `ByteString → T` |
| 回收 | `EventTracer` 自动 | `Register`/`UnRegister`(Recycle 退订) |
| 底层 | `EventPool` 队列 | ECS 网络栈(TCP/WS/Protobuf) |

### 7.8 设计要点
1. **双总线分层**:`服务器 → 协议总线(RegisterProtocol 落到某 Feature) → Feature 处理后 Fire(E_XXX) 事件总线 → UI/其它模块响应`,形成「网络 → 逻辑 → UI」清晰链路。
2. **ET 框架风格改造**:`NetEntity`(ECS 实体)/`ComponentFactory`/`GameNetworkComponent`/`Session`/`MessageDispatcherComponent`/`ProtobufPacker` + `AChannel`/`AService`(TCP/WebSocket/WebGL),是成熟手游网络层。
3. **RPC 序号关联**:`SerialNumber`(rpcId)配对请求/响应(类 gRPC);NRPC(序号 0)用于无需响应的单向请求。
4. **弱网健壮**:8s 发送超时、断线重发未完成 RPC、`ByteString` 复用、推送单 handler 避免重复消费。
5. **类型安全**:`Register<T>`/`CallRequest<T>` 全程泛型,反序列化由 `ParseMessageFrom<T>` 自动完成,业务层只拿到强类型 protobuf 对象。

## 8. 服务器下发 → MessageDispatch 路由链路

整条下行链路分 **5 层**,从 socket 事件一直到业务 Feature 的 `OnXxx(T msg)`。当前项目强制 `WebGLSocket`(WebSocket),以 WebGL 路径为主。

### 8.1 信封结构 `MessageWrapper`(一切的前提)
所有网络包都包一层 protobuf 信封(`Hotfix/PBStruct/Wrapper.cs`):
| 字段 | 含义 |
|------|------|
| `proto_id` (1) | 协议号(opcode) |
| `data` (2) | `ByteString` 真实消息体 |
| `serial_number` (3) | 流水号(rpcId);**0 = 服务器推送** |
| `received_serial_number` (4) | repeated,客户端已收到回应的 rpcId 列表(随下次请求回带服务端) |

因为统一封了信封,socket 层只需整体收发一个二进制帧,无需解析内部协议。

### 8.2 完整链路图
```
[UnityWebSocket] OnMessage(二进制帧)
   │  WGChannel.OnBinaryRecv(byte[] data)           ← 写 recvStream + 512KB 上限校验
   ▼
AChannel.OnRead(recvStream) → ReadCallback 事件
   ▼
Session.OnRead → Run → Network.MessageDispatcher.Dispatch(session, opcode=0, memoryStream)
   ▼
GameMessageDispatcher.Dispatch → handler.Invoke(session, 0, data)
   │  handler = MessageDispatch (NetMessageManager.Create 时注入)
   ▼  ╔══════════════ NetMessageManager.MessageDispatch ══════════════╗
      ║  wrapper = MessageWrapper.Parser.ParseFrom(bytes)              ║
      ║  rpcId = wrapper.SerialNumber                                  ║
      ║  ┌─ rpcId == 0 (推送 / NRPC响应) ─────────────┐                ║
      ║  │   _messageWrapperCallbacks[protoId] 有?     │                ║
      ║  │     → 唤醒 NRPC Task                        │                ║
      ║  │   否则 → MessageHandler(protoId, Data)  ←推送主路径          ║
      ║  └─────────────────────────────────────────────┘                ║
      ║  ┌─ rpcId != 0 (RPC响应) ────────────────────┐                ║
      ║  │   _rpcRecivedIds.Add(rpcId)                │                ║
      ║  │   _rpcWrapperCallbacks[rpcId] → tcs.SetResult ║ ← CallRequest 唤醒
      ║  └─────────────────────────────────────────────┘                ║
      ╚═════════════════════════════════════════════════════════════════╝
   ▼  (推送) MessageHandler
_messageHandlerMap[protoId]?.Invoke(bytes)
   ▼  闭包: msg = ParseMessageFrom<T>(bytes); action(msg)
业务 Feature.OnXxx(T msg)   ← Feature.RegisterProtocol<T> 注册的 handler
```

### 8.3 逐层说明
**① Socket 层 — `WGChannel`(`Network/WebGLSockets/WGChannel.cs`)**
- `WGService.ConnectChannel(url)` 建 `WebSocket` + `WGChannel`,订阅 `OnOpen/OnMessage/OnClose/OnError`。
- `OnBinaryRecv(sender, byte[] data)`:`data.Length > 512*1024` → `OnError(ERR_WebsocketRecvError)`(防大包);否则把整段 `data` 写入复用的 `recvStream`(取自 `RecyclableMemoryStreamManager`),`Seek(0)`,调 `this.OnRead(recvStream)`。
- **关键**:WebSocket 二进制帧边界 = 一个完整 `MessageWrapper`,无需额外分包。

**② Channel → Session — `AChannel.OnRead` → `Session.OnRead`**
- `Session.OnBuild` 时 `channel.ReadCallback += this.OnRead`。
- `Session.OnRead(MemoryStream)` → `Run` → `Network.MessageDispatcher.Dispatch(this, 0, memoryStream)`。
- 注意 opcode 传 **0**:不再用 ET 老式的「opcode 字段 + OpcodeTypeComponent」(`Run1` 是遗留),改用信封内 `proto_id`。

**③ Dispatcher — `GameMessageDispatcher`(`Framework/NetMessage/GameMessageDispatcher.cs`)**
- `Dispatch(session, opcode, message)`:`data = message as MemoryStream` → `handler.Invoke(session, opcode, data)`。
- `handler` 在 `NetMessageManager.Create()` 里被设为 `MessageDispatch`(`gameMessageDispatcher.handler = MessageDispatch`)。

**④ 路由核心 — `NetMessageManager.MessageDispatch`**
```csharp
wrapper = MessageWrapper.Parser.ParseFrom(bytes);   // 解信封
rpcId = wrapper.SerialNumber;
if (rpcId == 0) {                                     // 推送 / NRPC 响应
    if (_messageWrapperCallbacks.TryGetValue(wrapper.ProtoId, out t))  // NRPC 单向请求回调
        { LogRequestCost(...); _messageWrapperCallbacks.Remove(...); t.Item2.Invoke(wrapper); return; }
    MessageHandler(wrapper.ProtoId, wrapper.Data);    // ← 推送落地
} else {                                              // RPC 响应
    if (!_rpcRecivedIds.Contains(rpcId)) _rpcRecivedIds.Add(rpcId);
    if (_rpcWrapperCallbacks.TryGetValue(rpcId, out t)) {     // 唤醒 CallRequest 的 await
        LogRequestCost(...); _rpcWrapperCallbacks.Remove(rpcId); t.Item2.Invoke(wrapper); return; }
}
```
`MessageHandler(protoId, bytes)` 再查 `_messageHandlerMap`:命中则 `action.Invoke(bytes)`(即 `Register<T>` 存的闭包,反序列化成 `T` 后调业务);未命中 `LOG.Net.E("Not found handler for protobuf id")`。

### 8.4 TCP 路径差异(补充)
- TCP 无帧边界,需 `Network/TCP/PacketParser.cs` 做**长度前缀分包**(4 字节长度 + 消息体),`TService.Update()` 主动轮询;WebGL 则靠 WebSocket 帧边界、`WGService.Update()` 为空(由 `UnityWebSocket` 事件回调驱动)。
- `NetworkComponent.Update()` 每帧调 `Service.Update()`;`NetMessageManager.Update` 再调 `NetEntity.Update()` 转发。

## 9. MessageDispatch 路由设计意图

整条 `MessageDispatch` 路由围绕「**解耦、可靠、可演进**」三个目标做取舍。

### 9.1 总体意图:三层职责分离
```
网络栈(字节收发) → 协议总线(字节→强类型,按协议路由) → 业务 Feature(处理) → 事件总线(广播给 UI)
```
- 网络栈只管「字节怎么来怎么走」,**完全不认识业务协议**。
- `NetMessageManager` 是**唯一**把「字节」翻译成「强类型 protobuf」并把消息交给正确业务的地方。
- 这样换传输(TCP↔WebSocket)、换序列化、加协议,业务层(`Feature`)一行都不用改 —— 它只认 `T` 和 `EEvent`。

### 9.2 统一信封 `MessageWrapper` 的意图
1. **解耦 socket 与协议**:底层只需收发一个二进制 blob,不必知道里面是哪种协议、有没有 opcode 头。TCP(长度前缀分包)和 WebSocket(帧边界)因此能**共用同一套上层逻辑**。
2. **一个信封承载三类元信息**:`proto_id`(往哪路由)、`data`(负载)、`serial_number`(请求响应配对)、`received_serial_number`(可靠回带)—— 不引入额外自定义包头。
3. **与 protobuf 同构**:信封本身就是 `.proto` 生成类,序列化/反序列化零额外框架代码,跨端一致。

### 9.3 双键路由(`serial_number` vs `proto_id`)的意图
- **RPC 响应**(`serial_number != 0`):一问一答,必须靠 **rpcId** 把异步响应配对回原 `await` 调用(类 HTTP/2 stream-id、gRPC)。客户端**主动**发起。
- **服务器推送**(`serial_number == 0`):服务端**主动**、客户端被动监听,没有"原调用",只能靠 `proto_id` 直接分发到订阅者。
- **NRPC**(单向请求却想要回执):`serial_number=0` 但带响应,用 `proto_id` 配对(与推送共用 `_messageWrapperCallbacks`)。
> 意图:**用最契合消息语义的键路由**,RPC 用关联 id,NRPC/推送用协议号,互不污染。

### 9.4 单播(协议总线) vs 多播(事件总线)的意图
`_messageHandlerMap` 是**单播(每协议一个 owner)**,事件总线是**多播**:
- 一条服务器推送语义上**只该被一个业务归属处理**(某个 Feature 独占某协议),单播避免重复消费与歧义。
- 而"资源变化/功能开启"这类**需要多模块响应**的场景(UI、红点、活动都关心)交给事件总线 `Fire(E_XXX)` 去多播。
> 意图:**协议 = 点对点(单播),事件 = 广播(多播)**。两条总线让"网络进来的数据"和"需要被多个 UI 关注的变更"彻底分开。

### 9.5 三种消息收敛到一个 `MessageDispatch` 的意图
RPC响应/NRPC响应/推送 全在一个入口分支,而不是拆三个回调:
- socket 层看它们都是"一个信封字节流",差别仅在 `serial_number` 是否为 0。
- 收敛后**统一日志、统一耗时统计**(`LogRequestCost`)、统一错误处理,易维护、易监控。

### 9.6 生命周期安全的意图(与 `EventTracer` 对称)
`Feature.RegisterProtocol<T>` → `NetMessageManager.Register<T>` 入静态字典;Feature 销毁时 `Recycle → UnRegisterAllProtocols` 退订。
> 意图:与事件总线的 `EventTracer` 完全对称 —— Feature 声明"我关心哪些协议",框架保证销毁后**绝不会再收到指向已释放模块的数据**,杜绝弱网/重连时最常见的空引用崩溃。

### 9.7 `received_serial_number` 回带的意图(弱网可靠)
客户端把"已收到回应的 rpcId 列表"随下次请求发回服务端:
- 应用层**可靠确认**:TCP/WebSocket 本身可靠,但**断线重连后状态要重建**;回带列表让服务端丢弃已确认的未决项、按需重发,实现应用级去重/补偿。
- 与 `OnReConnect()` 把 `_rpcWrapperCallbacks` 里未完成请求重发的机制配套。
> 意图:在不可靠的移动网络(切后台/弱信号/小游戏热重启)上,提供**传输层之上的业务级可靠**。

### 9.8 主线程同步派发(为何不像事件总线那样入队)
事件总线 `Fire` 是**入队、下一帧处理**;协议总线推送却**同步即时**执行(UnityWebSocket 回调本就在主线程,直接 `handler.Invoke`):
- 推送是"游戏状态变更的直接源头"(如抽卡结果、战斗结算),需要**即时、确定、无一帧延迟**地落地到 Feature。
- 省去跨线程队列 + 锁,最自然也最高效。
> 意图:**状态来源必须同步重放,跨模块通知可以异步**。

### 9.9 WebGL/WebSocket 适配的意图
- 强制 `WebGLSocket`:小游戏/WebGL **不支持裸 TCP socket**,只能走 WebSocket;`TService`/`Run1`(依赖自定义 Packet 头里的 opcode)被放弃,改走**信封内 `proto_id`** 的路径。
> 意图:信封路径不依赖任何传输层自定义的包头,对 WebSocket 这种"帧即包"的协议天然友好,是更通用的演进方向(代码里 `Session.Run1` 即 ET 老式路径,已不被 `Run` 调用,留作兼容)。

### 9.10 移动端健壮性细节的意图
- **512KB 收包上限**:防异常/恶意大包导致移动端 OOM。
- **`RecyclableMemoryStream` 复用 `recvStream`**:高频网络包避免反复分配 → 降 GC,移动端关键。

### 9.11 设计意图一句话总结
`MessageDispatch` 路由本质是一个**"信封驱动、双键分流、单播到点"的应用层消息交换机**——把不可靠/异构的传输细节挡在门外,把字节 safely 变成强类型消息并精准投递给唯一业务归属,同时在信封里埋好 RPC 配对与应用级可靠确认的钩子,使整个网络层在弱网、小游戏重连、热更新回收等真实场景下依然健壮、可演进。
