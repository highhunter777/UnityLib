# M10 交付件硬编码与可扩展性审查（M11 前置，2026-09-19）

> 范围：RoomServer/* 与 Assets/LiteNet/**（M10 全部交付件）。
> 结论：**架构骨架合格，无阻塞性硬编码**；M11 前有 **1 个必修 + 3 个建议**，其余按 YAGNI 留档。

## 一、必修（M11 开工前）

### 1. `RollbackSim.OnAuthoritativeSnapshot` 和解重放丢失 `_lastInputs` 基线
- **位置**：`RollbackSim.cs` 和解重放段
- **问题**：Restore 权威 + 重放本地历史后，`_tickInputs`（下帧预测基线）未按重放后的输入链刷新——下一渲染帧 PrepareNext 的“沿用上一帧”取到的是**重放前**的陈旧值（预测与权威基线错位一帧）。
- **影响**：和解后第一帧预测错位（有界、下一快照纠回）——对跑测试未暴露是因为重放输入 ≈ 沿用链。
- **修法**：重放结束后从 `_history.TryGet(last)` 刷新 `_tickInputs`（一行）。
- **成本**：5 分钟。

## 二、建议（M11 中顺手做）

### 2. `Room.ExpectedPlayers = 2` 是**写死的房间容量**
- 现状：`const` 编译期固定，`_entityIds/_frameInputs/_playerSessions/IdentityTemplate` 全按 2 定容。
- M11 影响：4 人联机 demo（§9 M11 验收“4 人同房间”）前必须改为 **ctor 参数**（容量沿成员数组传播，改动面 ~6 处）。
- **建议**：M11 开工时改 ctor 参数 + `RoomConfig`（把 RoomId/端口/期望人数/seed 策略一并收口）——一次到位，不再逐个散改。

### 3. `Program.cs` 的 MVP 装配参数（端口 17777 / Room-A）
- 已支持 `--port` 命令行（并行线批③加的）✓；房间号仍写死 DefaultRoomId。
- 建议：M11 联调时补 `--room` 参数即可（一行）。

### 4. Ops 输出走 `Console.WriteLine`
- 无头验收够用；M11 联调建议 Ops 汇总改走委托回调（宿主决定打印或上报）——ServerHost 已有字段骨架，属小改。

## 三、核验通过（无需动）

| 项 | 证据 |
| --- | --- |
| 常量集中纪律 | 端口/房间号/预期人数均 `const` 收口（Program/ServerHost/Room 各自一处） |
| 协议单源红线 | RoomServer 直接 Compile Include LiteNet/Protocol——物理上无法双写（csproj 已验） |

## 四、明确不做（YAGNI 留档）

- 多房间并发压测/动态房间创建（MatchMaker 仍省——固定房间号够 MVP）
- Gate 的 `_pending` 字典无淘汰（对跑周期内帧号单调递增、容量随确认自然释放；长期运行若发现滞留再加清扫）
- Ops 的持久化/上报（Console 打印够 M11 联调）

——审查完。M11 开工时的落地顺序建议：**先做必修 1（5 分钟），再做建议 2（RoomConfig 容量参数化，M11 4 人房的前提）**，其余随 M11 各组件顺带。
