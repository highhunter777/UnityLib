## 0. 三条不可让步的原则

1. **Sim 层不认识 Unity**：`noEngineReferences: true`，不引用 `LiteFramework`，不进 HybridCLR 热更程序集，不碰 `Transform`/`Rigidbody`/`Animator`/`Time`/`Mathf`。
2. **依赖单向**：`View → Sim（只读）`。Sim 不反向持有 View，也不广播事件——View 每渲染帧自己来读。
3. **`Step` 必须是纯函数**：`Step(state, input) → state'`，无隐藏状态、无 IO、无静态可变量。这是预测、和解、服务器权威、复查重放**四处复用同一套 Sim** 的前提——见 §5.1。

## 2. 数值与确定性纪律（v3：float 版，定点数归帧同步预案）

> **v3 决策：状态同步不用定点数。** 依据：①服务器权威是单一运行时（.NET 8），float 单环境内确定；②客户端预测与服务器的一致性只影响**和解率**（体验指标），不再影响正确性（快照覆盖兜底）——定点数的核心收益（跨平台逐位一致）在状态同步下没有买单人；③**业界状态同步权威服务器全是 float**（CS2/OW/LoL），定点数是帧同步的专属资产。定点数全套设计（Q16.16/128 位乘/查表）**完整保留在帧同步预案**（§12.2），触发分支时按 v2 版 §2 实施——代价是 Sim 数值层重写，这是预案的已知成本，写进预算不是意外。

**记法映射**：本文其余章节的 `Fp` / `FpVector3` / `FP_DT` / `FpMath` 记法，在 v3 下分别读作 `float` / `SimVector3(float×3)` / 固定步长 `dt = 1f/60` / `SimMath`。

### 2.1 IEEE 754 的确定性边界（本节的知识支柱）

| 运算 | 跨运行时确定性 | 结论 |
| --- | --- | --- |
| `+` `-` `*` `/` | ✅ **标准要求正确舍入**——.NET x64 服务器与 Mono/IL2CPP ARM64 客户端结果一致（前提：不发生 FMA 融合、不启用扩展精度） | 放心用 |
| `Sqrt` | ✅ 同为 IEEE 基本运算，必须正确舍入 | 放心用 |
| `Sin`/`Cos`/`Atan2`/`Exp`/`Log` | ❌ **实现相关**（native libm 各家不同） | **禁用，走查表** |

由此 float 版纪律只有一条硬规则：**禁 `Math.Sin/Cos/Atan2` 等超越函数，一律走生成的查表**（`SimTrig`，float 表硬编码进代码——生成思路沿用原 FpMathTables，Editor 菜单产出、生成物入库、严禁运行期用 `Math.Sin` 填表）。其余基础运算直接用。

**两条配套纪律**：①服务器与客户端代码**禁用会产生 FMA 融合的写法**（不写 `a*b+c` 的显式 MathF.FusedMultiplyAdd，也不依赖编译器融合——默认不融合，写进 lint 清单）②不使用依赖精度的比较（`==` 比较 float 值一律改容差比较，防跨端末位差异把逻辑分支打歪）。

### 2.2 其余纪律（与 v2 相同，理由更新）

- **`SimRng`**：Xorshift64*（整数运算本就跨平台确定），种子由服务器开局下发，随机状态进快照。
- **确定性容器与遍历**：禁 `Dictionary` 遍历、禁不稳定 `Sort`、禁 LINQ、禁闭包分配、禁多线程——v3 理由：服务器权威（.NET）自身需要可重放复查（同环境重放必须一致），且客户端预测与权威越一致和解率越低（§10.2）。
- **checksum 序列化**：float 参与哈希必须先按位转 int（`BitConverter.SingleToInt32Bits`）——浮点哈希按位才有意义。
- **性能顺带收益**：float 加乘比 Q16.16 的 128 位乘快数倍，Sim 帧耗预算更宽。

## 3. Sim 层结构（rollback 倒逼的改版）

### 3.1 实体存储：固定容量槽位数组，不是 `List`

**这是 v1 与 v2 最大的结构差异。** v1 用 `List<SimEntity>` + 标记删除，对 rollback 不友好——快照涉及动态结构、恢复有分配、遍历顺序难保证。v2 改为**可整块拷贝的固定布局**：

```csharp
public const int MaxEntities = 256;

public unsafe struct SimWorldState {          // 全部 blittable，无引用类型，无 padding 歧义
    public int Frame;
    public ulong RngState;
    public EntitySlot Entities[MaxEntities];  // 固定槽位
    public uint AliveBitmap[MaxEntities / 32];
    public fixed byte Globals[256];           // 全局逻辑状态（比分、波次等）
}

public struct EntitySlot {
    public long Id;           // 稳定 id：slotIndex(低 16) | version(高位)。**64 位防重绕**——
                              // 16 位 version 在弹幕密集时约 20 分钟耗尽（投射物高频生灭，每秒几十次槽位复用），
                              // 重绕后跨帧引用（投射物目标、击杀统计）误认新实体，且表现为"偶尔目标错误"极难复现。
                              // 借鉴 ET/Fantasy 长 InstanceId 思想，成本 4B/实体（快照 +1KB），可忽略
    public FpVector3 Pos, Vel;
    public Fp Yaw;            // 俯视角朝向（射击必需）
    public int Hp;
    public uint Flags;        // 存活/无敌/开火中...
    public fixed byte Custom[32];  // 组件自定义状态，定长
}
```

> **2026-09-18 对账（本节示例与代码的三处差异，均为既有决策的落地结果，非新问题）**：
> ① `Fp` / `FpVector3` 是 **v2 定点数时代的记法**，v3 下按第 48 行的映射读作 `float` / `SimVector3(float×3)`——代码即 `LiteSim.Core/Scripts/EntitySlot.cs`（`SimVector3 Pos, Vel` + `float Yaw` + `int Hp` + `uint Flags`，`CustomData` 已按 M8 决策 #2 落为**平面数组**，不在 struct 内）。
> ② `Yaw` 自 **Aim 方向改造**起是 **Sim 内派生量**（由 `SimInputFrame.AimX/AimZ` 经 `SimTrig.Atan2` 在 `InputSystem` 派生；字段仍在、仍进快照与 checksum，表现层照旧消费）——见《角色状态与动作实现设计》§7-1。
> ③ 快照拷贝落地为 **`Array.Copy`** 而非 `UnsafeUtility.MemCpy`（后者属 Unity 程序集，`LiteSim.Core` 零引擎依赖拿不到；`Array.Copy` 即 memcpy 级且纯托管）——M8 决策 #1 改定，M9 全量兑现。

- **快照 = 整块拷贝**（`Array.Copy`，见上 ③），无 GC、无遍历、无顺序问题。
- 单快照约 16 KB（256 × 64 B），回滚深度 8 → `SnapshotRing` 常驻 128 KB，预分配。
- 分配实体 = 找空槽 + 版本号递增；释放 = 清 `AliveBitmap` 位。**不做 swap-remove**（打乱遍历顺序）。
- 遍历固定 `for (i = 0; i < MaxEntities; i++)` 跳过空槽——顺序恒定，且跳过的成本远低于顺序不稳定的代价。

### 3.2 逻辑帧：60Hz（射击要求）

射击对 30Hz 太敏感（33 ms 一帧，高速移动 + 精确瞄准手感差）。定 **60Hz**。

- 带宽估算（8 人房）：输入包 16 B；下行 `(16×8 + 头 8) + KCP/UDP 头 52 ≈ 188 B` × 60 ≈ **11 KB/s**，上行约 1 KB/s。可接受。
- `FP_DT = Fp.FromRaw(One / 60)` 恒不变量，不接受可变 dt。Sim 自备 `FrameDriver`（累加器 + 追帧），**不吃 `IGameClock`**（GameClock 可变速可暂停，服务于表现层）。

**FrameDriver 的驱动接缝（谁喂它）**：`FrameDriver` 在 `LiteSim.Core`（零依赖，不能实现 `ITickable`）——由 `SimView`（LiteSim.View，`ITickable`，§6.2）包装：`SimView.Tick` 内部跑 FrameDriver 累加器（快照校准 / 预测推进 → `Step` → 帧事件消费），`GameEntry` 照常统一驱动 ITickable 列表，**没有"主循环换手"这回事**。

**`BattleContext` 生命周期交接**：`ProcedureBattle.OnEnter` 创建（`new BattleContext`——SimWorld / FrameDriver / SnapshotRing / InputHistory，全部预分配）并挂进 SimView；`ProcedureResult` 或退战斗 `OnLeave` 时销毁（解绑快照流、停 FrameDriver、对象还池）。归属：**流程创建与销毁，不经容器**（§8.3 既定）。

### 3.3 系统执行顺序

显式注册顺序：`输入 → 移动/重力 → 碰撞 → 射击判定 → 投射物 → 伤害结算 → 冷却/Buff → 清理`。**不用自动扫描**（§3.2 同款纪律）。同帧多个射击请求按 `playerId` 升序处理，保证顺序确定。

### 3.4 射击的命中判定

- **Hitscan 为主**：`SimRaycast(origin, dir, maxDist)` 对圆柱体（半径 + y 区间）求交，纯 float 数学，确定性。射线结果按距离取最近命中。
- **投射物**（火箭/榴弹）作为实体槽位存在，随世界一起快照——rollback 天然正确，**不需要延迟补偿**。
- 同帧多次命中按 `playerId` 升序结算，伤害/死亡/得分全部进 `SimWorldState`。
- **穿透防护**：hitscan 无穿透问题；投射物单帧位移须 < 最小碰撞半径，Debug 断言。
- **命中判定的延迟策略：见 §3.4.1（服务器回溯，2026-09-10 定案）。**

#### 3.4.1 命中延迟补偿：服务器回溯（lag compensation，CS2/OW 同款）

**问题**：开火不预测（§5.3）+ 命中在权威当前帧判定 → 高 ping 玩家必须**提前量射击**（约插值延迟 66ms + RTT/2），且"我瞄中的目标"在服务器侧已走位。CS2/OW/全部竞技射击的解法是**服务器回溯**——把命中判定回溯到**开火者当时看到的画面时间**。定案采纳：射击手感是本玩法核心，无补偿（QuakeWorld 风）不该是隐含行为。

**机制**（复用既有设施，不新增大件）：

- **权威侧逐帧快照环**：AuthSim 每帧 Step 后 Capture 进服务端 `SnapshotRing`（复用 M9 同一个类），容量 = `LagCompHistory`（默认 **16 帧 ≈ 267ms**，`SimConfig` 旋钮；**0 = 关闭**，退化为提前量判定——留退路）。
- **开火者视角帧 = `Input.ackSnapshot` 对应的权威帧号 + 插值帧数**（`SimConfig.InterpFrames`，默认 2×快照间隔 ≈ 4 帧）。**由输入流推导、不用实测 RTT**——ack 本就在输入流里（§4.5 协议表），重放/复查天然可复现，确定性纪律不破。
- **判定流程**：处理开火命令 → 从服务端快照环 Restore 视角帧 → **对回溯后的目标位置做 Raycast（只读）** → 命中结果（伤害）写回**当前帧**权威状态。回溯只读、伤害即时，权威推进不变。
- **反作弊边界（两条 clamp）**：视角帧 clamp 到 `[处理帧 − LagCompHistory, 处理帧]`；`ackSnapshot ≤ 服务器已广播帧号`（服务器校验，§4.5）——捏造超大 ack 无法拉长回溯窗口。
- **与客户端预测的关系**：客户端**不预判延迟补偿结果**（开火本就不预测，§5.3）——本地只见 0 延迟开火反馈（§6.2），命中权威判定随后由快照同步，无需额外和解路径。

**里程碑**：M10（服务端快照环随 RoomServer 交付；`SnapshotRing` 本体是 M9 交付物的复用）。

### 3.5 y 轴：2.5D

XZ 平面圆形碰撞 + 静态障碍（AABB/圆）网格分桶；Y 轴只做跳跃重力积分 `vy -= g*dt; y += vy*dt; if (y <= groundY) { y = groundY; vy = 0; }`。不做斜面/地形碰撞，高低差用离散"平台高度"。视觉仍是完整 3D。

### 3.6 全量状态校验

```csharp
uint ComputeChecksum(in SimWorldState s) {   // FNV-1a 32，遍历顺序恒定
    uint h = 2166136261;
    h = Hash(h, s.Frame); h = Hash(h, s.RngState);
    for (int i = 0; i < MaxEntities; i++) {
        h = Hash(h, s.Entities[i].Id);
        h = Hash(h, s.Entities[i].Pos.X.Raw); /* …全部参与逻辑的字段… */
    }
    return h;
}
```

- 开发期每帧算并广播；release 每 10 帧一次。
- 不一致即：①`Log.Error` 带帧号与本端值 ②dump 前后输入日志 ③**暂停 Sim**（继续跑会污染后续诊断）。
- **v3 定位**：checksum 不再上服务器对账（权威快照覆盖兜底），转为**本地调试与复查重放**用——录制对局离线重放时 checksum 是一致性的裁判（§12/M12）。
- **漏字段是最常见的坑**：所有逻辑字段集中在 `SimWorldState` 内，`ComputeChecksum` 与它是同源的同一块内存——结构上杜绝遗漏（这是 §3.1 改用固定布局的额外红利）。

### 3.7 Sim 层不用事件中心：命令缓冲 + 帧事件缓冲

**Sim 层（两范式下）都不引入通用事件中心**——事件中心的四个核心特性在确定性边界内全是负资产：

| 事件中心特性 | 在 Sim 层的问题 |
| --- | --- |
| 动态订阅 | 派发顺序 = 订阅顺序 → 顺序不确定 → 不同步 |
| 待派发队列 | 队列是状态，却通常不在快照里 → 回滚后错乱 |
| 发布者不知订阅者 | Sim 的系统集合编译期就确定（个位数），这层解耦换不来收益，只换来顺序不可控 |
| 事件对象 + 闭包 | 破零分配纪律 |

**判断规则**：想要"运行时动态增删监听者"，基本说明设计错了——那应该是数据驱动（表里配 effect 列表）+ 固定分发。

三种需求各有去处：

| 需求 | 解法 |
| --- | --- |
| 需跨帧保存（存活 / CD / 比分） | 是状态，进 `SimWorldState` |
| 当帧延迟执行（伤害 → 死亡 → 掉落） | `CommandBuffer` |
| 告诉表现层（命中 / 暴击 / 开火） | `FrameEventBuffer`，逻辑帧末消费 |

#### 命令缓冲（Sim 内部）

```csharp
public struct SimCommand {
    public SimCommandType Type;   // Damage / Kill / SpawnPickup / AddScore
    public int TargetId, SourceId, Value;
}
public struct CommandBuffer {
    public const int Capacity = 512;
    public int Count;
    public SimCommand Items[Capacity];        // 定长预分配，零 GC
    public void Write(SimCommandType t, int target, int source, int value) {
        if (Count < Capacity) { Items[Count] = new SimCommand(t, target, source, value); Count++; }
    }
    public void Clear() => Count = 0;
}
```

顺序由 `FlushCommands()` 里**分批的先后**显式决定，不是由订阅顺序隐式决定。若 flush 中又产生新命令（击杀 → 掉落），做**固定轮次迭代（最多 3 轮）**而非 `while` 到稳定——轮次固定才是确定的。

#### 帧事件缓冲（Sim → View）

```csharp
public struct FrameEvent {
    public FrameEventType Type;   // Hit / Crit / Death / Fire / Explosion
    public int EntityId, OtherId, Value;
    public FpVector3 Pos;
}
// FrameEventBuffer 同构，Capacity = 256
```

**消费时机是本设计的关键**：不是渲染帧来读，而是**每个逻辑帧 `Step` 结束后立即消费并清空**——

```csharp
while (simFrame < targetFrame) {
    world.Step(inputs);
    _view.ConsumeEvents(world.Events, simFrame);   // 立即消费（受 silenceUntilFrame 保护，§6.2）
    world.Events.Clear();                           // 立即清空
    simFrame++;
}
```

三个好处：①**追帧不丢事件**——一渲染帧跑 5 个逻辑帧，5 帧的事件都能播，而不是只剩最后一帧 ②**不必进快照**——每帧末清空，回滚重放会重新填充，天然一致 ③**回滚重放天然正确**，配合 §6.2 静默即可。

#### 状态差分仍是主力

能推断的（血量、存活、位置）让 View 比 `prev`/`cur`（§6.1）。帧事件缓冲只承载**不可推断的离散事件**——`Hp` 从 100 掉到 70，可能是一发 30 也可能是两发 15，状态差分推不出来，这种必须走缓冲。

### 3.8 System 的声明式边界：借鉴什么、拒绝什么

ECS 有两个流派，别混：**数据导向 ECS**（Bevy/DOTS：SoA 组件数组 + 查询遍历 + 调度器）与**OOP 式 ECS**（ET/Fantasy：class 实体树 + 组件挂载 + 扫描式事件）。Sim 层各借鉴一部分。

#### 借鉴（不动存储，合计约 60 行）

**1. 全局域窄化签名——签名即权限**

System 不再全量拿 `ref SimWorldState`，按域传参：

```csharp
// 现在：全量，签名看不出碰没碰随机数
CollisionSystem.Run(ref _state);

// 窄化：没有 Rng 参数——想碰都碰不到
CollisionSystem.Run(ref _state.Entities, _state.AliveBitmap);
ShootingSystem.Run(ref _state.Entities, ref _state.Rng, inputs);
```

确定性审计直接写在签名上："谁能动 `RngState`"从口头约定变成类型约束。这是 AoS 存储下能拿到的最大一份声明式收益。

**2. `EntityIt`——零分配遍历辅助**

消除每个 System 手写的 `for + 跳空槽` 样板（忘跳就是脏数据）：

```csharp
public ref struct EntityIt { /* ref struct + ref return，零分配 */ }

var it = new EntityIt(ref state);
while (it.Next()) { ref var e = ref it.Current; /* ... */ }
```

可内建常用过滤（活体 / 阵营），**到此为止，不长成查询语言**。

**3. CommandBuffer 已是 ECS 同构物**：Unity DOTS 的 `EntityCommandBuffer` 与 §3.7 的 `CommandBuffer` 是同一思想（结构变更延迟到安全点统一应用）——方向本就对齐，无需动。

#### 拒绝（各有硬冲突）

| ECS 能力 | 为什么拒绝 |
| --- | --- |
| **并行调度**（数据导向 ECS 的最大卖点） | 确定性禁多线程（§2.4）；60Hz / 256 实体单帧 <0.5ms，无需求。分片式确定性并行与 SoA 化共用触发条件（见下与《自研框架设计方案》§7.4） |
| **依赖图自动排序** | 与显式顺序正面冲突：无依赖的 System 谁先仍要人工标注，绕一圈回到手写。顺序写在 `Step` 函数体里，就是确定性最直白的表达 |
| **访问声明 + 运行时拦截** | 单块 blittable 状态物理不可拆；拦截需把字段访问包成属性/方法，破坏整块 memcpy 前提 |
| **OOP-ECS 实体树 / 扫描式事件**（ET/Fantasy 形态） | class 实体树踩全部红线（堆分配 / 引用 / 字典遍历 / 不可整块快照）；`[Event]` 反射扫描与"显式注册"纪律冲突（§3.2/§8.3），IL2CPP 下 link.xml 要保全部处理器。**Fantasy 对 ET 的改进（codegen 替代反射）恰是我们已在走的路**——两条独立演化路线收敛于同一方向 |

#### SoA 触发条件（挂起项）

AoS（整块可快照）与 SoA（按组件分块、声明式访问）服务于两个王：**快照/回滚 vs 查询/审计**。现状 AoS 正确。满足任一才重评：

- 实体规模 > 1k，或组件类型 > 20，`Custom[32]` 塞不下、遍历占帧耗可测比例
- 出现真实可感的"按组件批量处理"需求（全场单位同一连续计算，Burst 收益显著）

到那天是**存储层重写级**决定（快照、checksum、槽位分配全动），Quantum 形态（可 blit + 组件分块兼得）是目标——**没有数据逼，不做**。

### 3.9 玩法判定的住址：进 Sim vs 留 LiteGame

《自研框架设计方案》§8.2 把技能/Buff/属性的"单机/表现形态"放在 LiteGame（IGameClock 时序执行器、AttributeService）。**联机形态下参与战斗判定的部分必须住 Sim**（随帧状态，可快照可和解），否则判定发生在权威之外。映射如下——与属性系统"两套、不共用"（设计方案 §8.2）同等待遇：

| §8.2 系统 | 留 LiteGame（单机/表现） | **进 Sim（联机判定）** |
| --- | --- | --- |
| **动作**（技能/冲刺/交互读条/死亡复活） | 释放意图采集（进 `InputFrame`）、技能栏 UI/CD 图标（读快照）、纯表现动画（IGameClock/ITimelineRunner） | **前摇计时、冷却、持续时间、判定帧、伤害结算、单主动作槽与中断规则**（`ActionState`，见《动作与特效设计》§1） |
| Buff | 图标 UI、表现层粒子 | **时长、tick 结算、叠加层数、互斥**——随实体进快照 |
| 属性 | `AttributeService`（面板/战力展示） | **战斗数值**（攻击/血量/移速）内嵌槽位（§3.1） |
| 任务/成就 | 全部（非战斗，事件驱动） | 无 |
| 剧情/引导 | 全部（IGameClock 时序执行器） | 无 |

**判定原则一句话**：结算结果会被其他玩家感知的（伤害/位移/生成物），必须从 Sim 走；只有本人看得见的（UI、动画、音效），留 LiteGame。

**ITimelineRunner 的消费者迁移**：联机形态下其头号消费者（**动作时序**：技能/冲刺/交互读条等，见《动作与特效设计》）迁入 Sim（固定步长 + `CommandBuffer`），剩余消费者为**剧情/引导/单机 demo**——三件排期不变，但 M5 之后深耕技能系统时，**判定代码从一开始就写进 Sim 形态**，避免 M8 后二次迁移。

## 4. 网络层：KCP 双通道

### 4.1 传输选型

用 **kcp2k**（纯 C#、MIT、久经 Mirror 验证），vendor 进 `Assets/LiteNet/Vendor/kcp2k`。**不自研 KCP**——2000+ 行协议实现，自研零收益且易出微妙 bug。

### 4.2 关键决策：两个通道，不是一条可靠流

射击 + rollback 对延迟极敏感，而 **KCP 的顺序保证对逐帧输入有害**（队头阻塞：一个丢包会卡住后续所有已到达的输入）。因此：

| 通道 | 用途 | 机制 |
| --- | --- | --- |
| `NetChannel.Reliable` | 房间信令：Join / StartGame(种子、玩家列表) / 重连请求与响应 / 结算 | KCP 可靠有序 |
| `NetChannel.Unreliable` | **逐帧输入** | 裸 UDP + 冗余（每包带最近 4 帧输入），**不入 KCP 队列** |

kcp2k 原生支持 `Send(data, KcpChannel.Reliable | Unreliable)`，无需自己分 socket。

> 若坚持单通道全走 KCP：配置 `nodelay(1, 10, 2, 1)`（10 ms interval、快速重传 2、关拥塞控制）、`sndwnd/rcvwnd = 256`、`mtu = 1200`。代价是丢包时输入被队头阻塞，rollback 触发频率上升。**不推荐**，但留作退化路径。

### 4.3 拓扑：客户端-服务器权威（状态同步）

```
Client ──Intent(本地输入) [Unreliable+冗余]──▶ RoomServer(权威 Sim 60Hz)
Client ◀──StateSnapshot(增量，30Hz，**AOI 过滤**） [Unreliable]── 各自
        ◀──信令/结算/重连快照 [Reliable]──┘
```

服务器运行**同一份确定性 Sim 作为权威**（直接引用 `LiteSim.Core`——纯 C# 零依赖在 .NET 8 下原生可跑，`noEngineReferences` 的红利兑现），**广播状态快照**；客户端用同一套 Sim 做预测（本地玩家）与插值（远端玩家）。

用 P2P 锁步可以省掉服务器，但断线/重连/中途加入都要另想办法，且没有权威结算。**RoomServer 从第一天就是权威模拟器**——它同时是调试基础设施（单机模式 = 本地权威）和运营底线（反作弊/结算/复查）。

### 4.4 定帧与追帧

```
targetFrame = latestAuthoritativeFrame - inputDelay + 1
while (simFrame < targetFrame && steps < MaxCatchUp) { Step(); simFrame++; }
```

- **inputDelay = 1 帧**（16 ms @60Hz）——客户端预测下可以很小，这是状态同步相比 lockstep 的核心收益。做成 `SimConfig` 可配旋钮，先定 1。
- **MaxCatchUp = 5** 逻辑帧/渲染帧。持续落后则表现层轻微加速平滑，绝不无限追（假死比卡顿更糟）。

### 4.5 RoomServer 结构（.NET 8 控制台，单进程多房间，权威 Sim）

**职责：权威模拟 + 状态广播。** 服务器对每帧输入跑**同一份 Sim 并作为唯一真相**，以增量快照广播状态。三形态边界（防概念漂移）：

| 形态 | 服务器状态是唯一真相？ | 判定 |
| --- | --- | --- |
| 纯中继 | — | 无验证无结算。业界独立/休闲阶段常态，**本方案已弃** |
| 影子 Sim | ❌ | 帧同步的记账员形态——**v2 的选择，v3 降为预案**（§12） |
| **权威 Sim（本方案）** | ✅ | 状态同步：服务器广播状态快照，客户端预测/插值。业界对标：荒野乱斗、LoL、OW |

**能力边界要写明**：权威 Sim 能从根上杜绝"客户端改状态"类作弊（客户端无权威），但抓不住"合法输入的自动化"（脚本走位）——那是行为分析领域的事，别指望 Sim 层。

```
RoomServer
├─ Acceptor            KCP 监听：握手 → token/buildHash 校验 → 建 Session
├─ SessionManager      连接表、心跳、超时踢除、断线标记
├─ RoomManager         房间创建/销毁、成员表（playerId ↔ session）
│   └─ Room
│       ├─ AuthSim           引用 LiteSim.Core：60Hz 权威 Step（输入=收到的+缺席沿用），唯一真相
│       ├─ SnapshotDiffer    增量快照：变化槽位提取 + 量化 + 序号（vs 全量 16KB；30Hz 广播起步）
│       ├─ InputHistory      输入环形历史——复查重放 + 重连补发（§5.6）
│       └─ Relay             双通道分流：信令 Reliable / 输入与快照 Unreliable+冗余
├─ MatchMaker          MVP 可省：固定房间号 / 好友码；后续快速匹配
└─ Ops                 日志 + 指标：房间数、在线、快照大小/间隔、丢包率、和解率（客户端上报）
```

**关键机制**：

1. **快照是"尽力广播"**——到点就发，迟到输入进下一帧的权威 Step；快照丢失靠下一份累积补偿（§10.11），客户端绝不阻塞等快照（预测在跑）。
2. **掉线不停帧**——掉线者输入记空/沿用，他人照常玩；重连走 §5.6（权威快照直接恢复）。
3. **权威 Step 定序**：60Hz 到点 → 聚合本帧输入 → `AuthSim.Step` → SnapshotDiffer 生成增量 → 广播。**结算（胜负/伤害/比分）以权威结果为准，客户端只做展示。**
4. **和解率是首要健康指标**：客户端上报"快照与本地预测不符"频率（Ops 汇总）。持续偏高 = 预测与权威发散（输入模型问题），比不同步更早暴露。
5. **版本一致性（服务器端）**：`Join` 时客户端上报构建 hash，与服务器 Sim 构建 hash 比对，不符拒绝进房。
6. **输入校验分两层（2026-09-10 补，权威反作弊第一层）**：
   - **传输/会话层（RoomServer）**：输入频率限制（每逻辑帧至多 1 条/玩家，多余丢弃）、`ackSnapshot` 单调且 ≤ 已广播帧号（§3.4.1 反作弊 clamp 的执行点）、非法帧号丢弃。**只挡"传输层可见的非法"**。
   - **Sim 输入 System 内（确定性校验）**：移动向量长度 clamp、开火间隔与射速表校验——**必须在 Sim 内 clamp 而不是服务器拒绝**：客户端预测跑同一份 Sim，若只有服务器拒绝，本地预测与权威行为分叉 → 和解风暴。Sim 内 clamp 天然两端一致（服务器还白得单机模式同款校验）。
7. **AOI 兴趣管理（2026-09-10 定案引入）**：网格过滤（AoiCellSize/AoiRadius 旋钮）在广播前按各客户端观察位置裁剪增量快照；**只影响广播、不影响权威判定与回滚重放**（命中判定用全量状态）。视野覆盖全图时等价关闭。**协议序列化 = protobuf（代码生成）**：`.proto` 单源 → protoc 产出 C#，两端共用；`Input/StateSnapshot` 等全部包走 proto 定义（SlotDelta 用 zigzag + 量化整型表达），带宽较手写位压缩约 +25%，换取 schema 单源与演进安全。

**成立前提与成本**：

- `LiteSim.Core` 纯 C# 零依赖 → .NET 8 原生可跑（`noEngineReferences` 的红利兑现）
- **确定性从生命线降级为质量指标**：预测与权威同构（同一套 Sim）→ 和解罕见 → 体验平滑；偶发不一致被快照覆盖，**不发散、不崩盘**——项目最大技术风险（跨平台确定性长尾）就此移除
- 服务器多房间并行安全：房间间零共享状态，每房间单线程 Sim
- 成本：每房间 Sim 60Hz 步进 <0.5ms + 增量快照生成，单进程几十房间无压力

**协议面**（双通道沿用 §4.2；**序列化 = protobuf 代码生成**——`.proto` 单源进 LiteNet/Proto，protoc 产出两端共用 C#，包字段演进走 proto 演进规则；link.xml 追加 Google.Protobuf 段）：

| 方向 | 包 | 通道 |
| --- | --- | --- |
| C→S | `Join(roomId, token, buildHash)` | Reliable |
| C→S | `Input(frameNo, wire, ackSnapshot)` | Unreliable+冗余 |
| C→S | `MismatchReport(frameNo)`（和解发生时上报，供 Ops 汇总和解率） | Unreliable |
| S→C | `JoinAck(playerId, members)` / `StartGame(seed, configHash)` | Reliable |
| S→C | `StateSnapshot(frameNo, 增量槽位[+全量兜底], ackInput)` | Unreliable+冗余（30Hz 起步，`SimConfig` 旋钮） |
| 双向 | 心跳 / `Leave` | Reliable |
| C→S | `ReconnectReq` | Reliable |
| S→C | `ReconnectResp(authoritativeSnapshot, history)`（§5.6） | Reliable |

### 4.6 服务器选型：为什么不用现成服务器框架，以及可替换性

**不用 Fantasy/ET 类逻辑服务器框架，自研约 600 行**（kcp2k server 端打底）。三条理由，第一条足以定案：

1. **协议必须单源**：`LiteNet` 是客户端与服务器共用的程序集——协议只写一遍。若服务器用 Fantasy 的网络与消息系统，协议双写，"两端逐字节一致"的偏执第一天破防。**协议单源的价值高于任何服务器框架的功能。**
2. **节拍必须自控**：AuthSim 要求精确 60Hz 节拍与确定顺序的 Step。Fantasy 的 Timer/EventSystem/协程为逻辑开发便利设计，调度时序是框架内部行为——权威 Sim 的节拍不能寄放在别人的调度器里。自研驱动就是 `PeriodicTimer` 裸循环，节拍完全自控。
3. **需求错位**：Fantasy 是"服务器跑大量游戏逻辑"的全家桶（Entity / Actor / AOI / DB / 热重载），我们是"转发 + 权威模拟 + 增量广播"——它的核心能力零消费者，却要付全家桶依赖、学习成本、协议双写三笔代价。

**自研成本明细**：传输（kcp2k server 端——客户端已在用同一库，零新依赖）~100 / Session 心跳 ~100 / 房间管理 ~100 / FrameAggregator（`PeriodicTimer` 60Hz）~100 / AuthSim ~50（`LiteSim.Core` 直接引用）/ SnapshotDiffer 与历史 ~130，**合计 ~600 行**。

**何时 Fantasy 变对**（B 类判断，v3 修正——原判据"做状态同步游戏"已命中但我们仍不用，说明它写错了）：

1. **对局服务器之外还要养复杂业务服务**（大厅 / 社交 / 持久化 / 大规模世界 AOI）——那是服务器框架的主场（Entity / Actor / DB 生态有真实消费者）；注意形态是**新增服务进程**，不是重写对局服务器；按服务拆分后各自选型，**对局服务器保持薄**。
2. 团队愿意承担协议双写的治理成本，且 Fantasy 的 Actor 生态价值 > 治理成本。

**v3 语境下的重评估结论**：范式反转让服务器有了真实逻辑（权威 Sim），但结论不变——原因不是"逻辑少"，而是**核心管线必须紧贴 Sim 存储**：权威 Step 读 `SimWorldState` 槽位、增量快照按槽位 diff，这条路径与 blittable 内存布局焊死；Fantasy 的 Entity/Component 与我们的槽位是**同一职责的竞争实现**，引入它 = 服务器维护第二套实体语义。Fantasy 有消费者的部分（网络 / Session / Timer）已被 LiteNet + `PeriodicTimer` 覆盖。

#### 可替换性：两刀与一条红线

若未来真要换 Fantasy（或任何服务器框架），业务核心 60% **本来就不换**——协议打包、FrameAggregator、AuthSim、SnapshotDiffer、历史，Fantasy 一件都不提供，无论用什么框架都得自己写；换的只是"壳"（传输与会话）。为此现在付两刀：

1. **`LiteNet` 内部分层**：
   ```
   LiteNet/
   ├─ Protocol/     打包解包 / InputWire / 信令序列化——纯函数，零 IO 零状态零 kcp2k 依赖
   └─ Transport/    kcp2k 收发、双通道、冗余、Session——唯一允许碰 kcp2k 的地方
   ```
   纯目录整理，零代码改动；换任何传输框架，`Protocol/` 原封不动。
2. **房间业务组件依赖窄端口**：`IRoomTransport`（`Broadcast` / `SendTo` / `OnData`，3 个方法），`FrameAggregator` / `AuthSim` / `SnapshotDiffer` 依赖它而非 `KcpServer`。约 20 行。

`AuthSim` 天然可移植：只依赖 `LiteSim.Core`（零依赖纯 C#）——零依赖设计的第三次兑现。

**一条红线：换任何服务器框架，其网络层只许当 byte 管道用，绝不用它自己的消息系统**——否则协议双写回归，切换的全部意义清零。

诚实的成本警告：代码切换约两天，**运维与版本对齐体系重建是一两周**（buildHash 校验、指标、部署脚本都要重做）。而最可能的"换"形态是新服务用 Fantasy、中继不动——当前结构已天然支持，故**不做更重的预埋**（抽象服务器框架层、依赖倒置壳：数百行，为一个可能不发生的重写付复杂度，不值）。

## 5. 预测、和解与回滚（机制库）

> v3 定位：本章机制（SnapshotRing / InputHistory / 回滚重放 / View 重对齐）是**预测与和解的机制库**——状态同步主路线下，回退源为**服务器权威快照**、重放范围缩小为**本地输入**；帧同步预案（§12）下回退源为本地快照环、重放范围为全体输入。**机制同一套，只是参数不同。** 模型参考 GGPO 与 OW 的预测/和解。

### 5.1 前提：`Step` 必须是纯函数

rollback 成立的条件比"确定性"更严：

- **所有随帧变化的状态都在 `SimWorldState` 里**。System 只允许持有**不随帧变**的配置（射速、伤害表引用等）。
- 禁静态可变字段、禁缓存跨帧的中间结果、禁 System 内成员随帧累加。
- **两个缓冲都是"每帧生命期"**：`CommandBuffer` 帧末 flush 后清空、`FrameEventBuffer` 帧末被消费后清空——**`Step` 开始时两者必须为空**。这是它们可以不进快照的唯一前提；新增 System 时若破坏这点，回滚必然发散（§3.7）。
- 违反的后果不是"偶尔不同步"，而是**回滚重放必然发散**——比 lockstep 时代更早暴露，反而是好事。

### 5.2 快照环形缓冲

```csharp
public sealed class SnapshotRing {
    public SnapshotRing(int capacity, int stateSize);   // 预分配，运行期零分配
    public void Capture(int frame, in SimWorldState s);
    public bool TryRestore(int frame, out SimWorldState s);   // 超出缓冲范围返回 false
}
```

- 容量 = `MaxRollbackFrames + 1`（默认 9，即回滚深度 8 + 当前）。
- 每帧 `Step` 前 `Capture(simFrame)`。16 KB × 9 = 144 KB 常驻。
- 恢复用 `MemCpy`，16 KB 拷贝在现代硬件上是微秒级；回滚深度 8 → 单次回滚约 128 KB 拷贝 + 8 次 `Step`，完全在预算内。

### 5.3 输入预测策略（射击的关键取舍）

| 输入项 | 是否预测 | 理由 |
| --- | --- | --- |
| 移动向量 `MoveX/MoveZ` | ✅ 沿用上一帧 | 连续量，猜错代价小，回滚后位移修正不明显 |
| 朝向 `AimX/AimZ` | ✅ 沿用上一帧 | 同上；且朝向修正由表现层插值吸收 |
| **开火 / 技能按键** | ❌ 不预测 | **离散事件，猜错代价极大**——凭空多出一发子弹，回滚后凭空消失，玩家能看到明显的"回退" |

预测标记记录在 `InputFrameSet.IsPredicted[i]`，回滚判定只看它。

### 5.4 回滚触发与执行

```
收到 frame F 的真实输入：
  if (F < simFrame && 该帧曾用预测输入 && 与真实输入不符) {
      target = F - 1
      Restore(target)                       // 快照回退
      for (f = F; f <= lastSimulatedFrame; f++)
          Step(inputHistory[f])             // 用真实/已修正输入重放
      simFrame = lastSimulatedFrame
      View.Realign(simFrame)                // §6.2
  }
```

- **`MaxRollbackFrames = 8`**（133 ms）。超出则强制等待，退化为 lockstep 卡顿——这是正确性优先的兜底。
- 回滚后 `ComputeChecksum` 应与"从一开始就用真实输入跑"的结果一致。**这本身是一个绝佳自检**：预测正确时 checksum 不应变化。
- 单渲染帧回滚次数上限 2，防止雪崩。

### 5.5 输入历史

`InputHistory` 环形数组保存最近 32 帧的全体输入（真实 + 预测），供重放使用。预测输入在收到真实值后就地覆盖。

### 5.6 断线重连（权威 Sim 的直接受益者）

**首选路径**：服务器权威 Sim 持有最新状态 → `ReconnectResp` 直接下发**权威快照 + 后续输入历史**，客户端恢复后追帧——瞬时完成。

**降级路径**：版本不符或快照缺失时，退回重放全部输入快进（确定性 Sim 的固有红利）。

M11 实现，两条路径都要能走。

## 6. 表现层（View）

### 6.1 镜像与插值

- **插值延迟 = 2×快照间隔**（30Hz 快照 → 66ms jitter buffer，`SimConfig.InterpFrames` 与 §3.4.1 共用同一旋钮）。快照断流在 2 个间隔内由插值容忍，超限 snap 到最新权威帧。
- 每个逻辑帧结束拷 `cur → prev`；渲染帧按 `alpha = accumulator / FP_DT` 插值位置与朝向。
- 跳变（位移 > 2 m、实体新增/消失）直接 snap，不插值。
- 动画/特效/音效由 View **观察状态变化**触发（如 `cur.Hp < prev.Hp` → 播受击），Sim 不派发事件。
- **离散事件走 `FrameEventBuffer`**（命中 / 暴击 / 开火 / 拾取——状态差分推不出来的那些），见 §3.7；View 可再转成 C# 事件广播给 UI 与 Lua，但必须受 `silenceUntilFrame` 保护。

### 6.2 回滚后的表现层重对齐（rollback 最烦的部分）

```csharp
public sealed class SimView : ITickable {
    public void Realign(int simFrame) {   // 回滚后调用
        // ① snap 到当前逻辑状态 ② 清空 prev/cur 插值基准 ③ 重置累加器
        // ④ silenceUntilFrame = 回滚前已渲染到的帧号
    }
}
```

- **特效/音效不回滚**（已播的不撤销），但要**避免重播**：
  `silenceUntilFrame` = 回滚前已渲染帧号。重放期间所有"观察式触发"的特效/音效静默；重放结束、帧号重新超过 `silenceUntilFrame` 后才恢复。这比维护"已播放事件集合"简单得多，且不会漏。
- **本地玩家的和解修正走误差衰减，不 snap**（2026-09-10 补，Source 风格）：和解后的位置差 `residual = 权威位置 − 本地预测位置` 由 View 层持有一个偏移量，**~100ms 内衰减到零**（视觉平滑）——频繁小误预测若直接 snap，本地角色会持续微抖。**远端实体与朝向修正仍 snap**（本来就在插值里，snap 被插值吸收）。
- **开火反馈的 0 延迟**：本地按键 → 立即播枪口火焰与音效（纯 View 层，不碰 Sim）。命中特效则等 Sim 该帧判定结果出来再播。这就是射击手感与逻辑正确性的分工线。
- 相机固定俯角跟随，目标取插值后位置，`Cinemachine`（框架不封装，§8.4 既定）。

### 6.3 View 层可自由使用引擎

`float`、`Mathf`、`Rigidbody`、粒子、`Animator`、DOTween 全部可用。**唯一红线：绝不回写 Sim。**

## 7. 框架层如何承载网络（回答"框架层怎么做网络"）

**结论：框架不实现网络，只定义网络的挂点——接口契约 + 生命周期 + 驱动。** 实现全在 `LiteNet`。玩法侧的模式差异（俯视角射击 / FPS）以**策略包**收口，见 §14（v3.4）。

这与 §1.2「网络管理器砍掉，做联机时独立成插件，协议层不依赖框架」是同一条决策的落地：框架认接口，不认协议；不知道帧号，不知道 `InputFrame`。

### 7.1 框架层只放契约（接口在 `LiteFramework.Unity`，枚举在 Core）

> 落位说明：`INetworkService` 含 `UniTask` 签名，Core 是 `references: []` 引不了 UniTask，故接口居 Unity 层、纯数据枚举（`NetState`/`NetChannel`）留 Core。**`LiteNet` 禁 UniTask**——Server（.NET 控制台）与客户端共用它，UniTask 依赖 PlayerLoop 在 .NET 不可用；LiteNet 的异步只用 BCL `Task`。桥接（`KcpNetworkService : INetworkService`）发生在 LiteGame。

```csharp
public enum NetChannel { Reliable, Unreliable }        // 双通道，射击+rollback 的关键

public interface INetworkService : ITickable, IModuleStats {
    NetState State { get; }                            // Disconnected/Connecting/Connected/Error
    UniTask ConnectAsync(string host, int port, CancellationToken ct);
    void Send(ReadOnlySpan<byte> data, NetChannel channel);
    void Disconnect();
    event Action<NetState, string> OnStateChanged;      // 状态与错误原因
    event Action<byte[], NetChannel> OnReceive;         // 收到一包（已按通道分流）
}
```

约 30 行，**这是框架为网络付出的全部代价**。

### 7.2 三点接法

| 关注点 | 归属 | 做法 |
| --- | --- | --- |
| **驱动** | 框架 | 网络实现 `ITickable`，由 `GameEntry` 统一驱动收发轮询。**当前不开网络线程**（60Hz 小包够用）；若按需引入收包线程，结果必须经 `IMainThreadDispatcher.Post` 回主线程（《自研框架设计方案》§7.4 边界规则） |
| **生命周期** | 框架 FSM | `ProcedureLaunch` 注册 `INetworkService` 实现；`ProcedureMatch` 调 `ConnectAsync`；退出战斗 `Disconnect`。**连接状态变化由 Procedure 响应，不由容器管理** |
| **诊断** | 框架 | 实现 `IModuleStats` → HUD 显示 RTT/丢包/收发速率 |
| **协议语义** | `LiteNet` | 帧号、输入打包、冗余、重连——框架一概不知 |

### 7.3 红线

- 框架层**禁止**出现 `InputFrame`、`frameNo`、`RoomServer` 等概念——那是 `LiteSim`/`LiteNet` 的事。
- 薄壳服务与 UI **禁止**直接引用 `INetworkService` 发业务包，一律经玩法层（如 `IBattleService`）封装。

## 8. 生命周期归属：自研框架 vs DI 容器

### 8.1 两者管的根本不是一回事

| 维度 | 自研框架 LiteFramework | DI 容器（VContainer 型） |
| --- | --- | --- |
| 管的是什么 | **时间**：何时被驱动、处于哪个阶段 | **存活范围**：实例活多久、谁共享它 |
| 单位 | 骨架件 + 薄壳服务 + Procedure | 注册项（Registration） |
| 创建 | `GameEntry.Awake` 里 `new` → `RegisterInstance` | 首次 `Resolve` 惰性构造 |
| 销毁 | 进程结束（`DontDestroyOnLoad`，活一辈子） | Singleton=根容器释放；Scoped=子作用域释放；Transient=不管 |
| **阶段语义** | **有**：Lua 注册表填充期/解析期、Procedure 阶段（属流程层） | **无**——容器没有"游戏处于哪个阶段"的概念，也没有运行时开关模拟它 |
| 驱动 | `ITickable.Tick(realDelta)`，`GameEntry` 统一喂 | `EntryPoint`（`IStartable`/`ITickable`）自挂 PlayerLoop |
| 作用域层级 | 无（扁平单例） | `LifetimeScope` 父子层级，可动态 `CreateChild`/`Dispose` |
| 多例 | 不归它管 → 对象池 / `new` / Lua 注册表 | Transient / Scoped |
| 顺序保证 | **显式**（ITickable 列表顺序 = 装配顺序） | 注册/解析顺序，不显式 |

**结论：两者正交，不是替代关系。** 阶段语义属于流程层，容器补不了也不该补；框架也不需要容器的存活范围管理——因为它唯一的多例需求被对象池和注册表接管了。

### 8.2 三个真实冲突点

1. **`EntryPoint` 与 `ITickable` 重叠** → 两套 tick 体系。选自己的（`GameEntry` 统一驱动，顺序显式）。
2. **容器的 `Scoped` 与"每局战斗"看似对应** → 见 §8.3，这个需求其实被确定性纪律消解了。
3. **容器的 Diagnostics** → 本框架的诊断口径是**解析时点当场抛**（未注册 / 循环依赖含链 / 重复注册 / 构造抛真因），不做构建期全量预检（原 `Validate()` 已于 2026-09-10 决策删除，见《M1实施指导》§1）——零独立件、零成本。

### 8.3 射击 + rollback 下各对象的生命周期归属

| 对象 | 存活范围 | 归属 |
| --- | --- | --- |
| EventCenter / Log / FileSys / Setting | 全程 | DI Singleton |
| IConfigService / AssetService / UI 壳 / 声音壳 | 全程 | DI Singleton |
| `INetworkService` | 全程（连接状态可变） | DI Singleton |
| 房间流程 Procedure | 全程（FSM 切状态） | FSM 管理，非容器 |
| **`BattleContext`（一局）** | 一局 | **显式对象，非容器** |
| **`SimWorldState` + `SnapshotRing` + `InputHistory`** | 一局 | `BattleContext` 显式 new，**禁入容器** |
| Sim 实体（子弹/玩家） | 局内频繁增删 | `SimWorldState` 固定槽位数组 |
| View 实体 GameObject | 一局 | `UnityEngine.Pool` 对象池 |
| Lua UI 逻辑表 | 全程 | Lua 逻辑注册表 |

**关键推论：唯一的非全程作用域是 `BattleContext`，而它恰恰被 §3.1 的确定性纪律排除在容器之外**（容器的 `Dictionary` 注册、解析顺序依赖、作用域销毁的不确定分配，全踩红线）。所以——

> **射击 + rollback 不但没有制造新的 Scoped 需求，反而把最后一个潜在需求消解了。容器不需要加生命周期。**

### 8.4 DI 补强清单（不变，收益排序）

| 补强 | 行数 | 备注 |
| --- | --- | --- |
| `RegisterFactory<T>(Func<IServiceContainer,T>)` | ~20 | 覆盖延迟构造，比加生命周期便宜得多 |
| 重复注册抛异常 | ~5 | 现在静默覆盖，迟早踩 |
| Transient / Scoped / 属性注入 / AOP / 自动扫描 | — | **不做**（§2.1、§3.2 已定，理由见 §8.3） |

> 备注：VContainer 仍在维护（1.19.0 / 2026-07），不选用它是架构选择（避免第二套生命周期体系 + 学习目的），非不可用。

## 10. 风险与红线（v3：确定性纪律降级为质量指标，工程红线保持）

1. **Sim 层禁 `UnityEngine`**——`noEngineReferences: true` 是执行者，不是提醒；也是 Server（.NET）复用 Sim 的前提。
2. **Sim 层数值纪律（v3：float 允许，边界不可越）**：允许 `float`/`Mathf` 基础运算（IEEE 基本运算跨运行时确定）；**禁 `Math.Sin/Cos/Atan2/Exp/Log`**（native libm 实现相关）——超越函数一律走 `SimTrig` 查表；禁 FMA 显式使用与精度敏感比较（容差比较替代 `==`）；禁 `Random`/`DateTime`/`GetHashCode`/`Dictionary` 遍历/LINQ/闭包分配——Editor 菜单一键 lint 预警（§2.1 IEEE 边界表）。
3. **`Step` 必须是纯函数**（§5.1）——System 禁持随帧可变状态。v3 理由：预测、和解、服务器权威、复查重放**四处复用同一套 Sim**，任何隐藏状态都会让其中一处行为分叉。
4. **禁止热更触碰 Sim 与 Net**——启动期校验程序集构建 hash；服务器与客户端 Sim 版本对齐（`StartGame` buildHash 比对）。
5. **禁止 Lua 参与逻辑判定**——只能读 `Bridge.sim` 只读快照（把 §5.3「判定时序不跨语言逐帧回调」升格为红线）。
6. **命中/伤害结果以服务器权威为准**——客户端预测可立即表现枪口火焰与弹道（View 层 0 延迟反馈），但命中特效等**权威确认后再定**；预测的命中在和解时可能消失，绝不能让表现层先入为主（§5.3 的 v3 形态）。
7. **和解频率与追帧/回滚上限是硬约束**——和解触发率是首要健康指标（持续 >10% 说明预测发散，查输入模型）；防雪崩，假死比卡顿更糟。
8. **Sim 不做任何 IO**——日志走委托，release 空实现。
9. **`NetChannel` 分流不可省**——输入走可靠通道会引入队头阻塞，直接毁掉预测的延迟收益。
10. **快照率 / `inputDelay` / 插值缓冲是手感旋钮**——改动必须重跑 M9 的一致性用例与 M10 的和解率观测。
11. **增量快照必须带序号与丢包容错**——快照丢了用下一份全量/累积补偿，客户端绝不阻塞等快照（预测在跑，快照只是校准）。
12. **客户端自持进度在联机形态下是作弊洞**——存档/货币/物品若由客户端 FileSys 权威自持，改档即改事实。MVP（朋友局/局域网）豁免，**上线前必须服务器权威化**（§13.3，进度变更单 → 独立进度服务）；挂名于此，防"先上线再说"。

## 12. 范式对照与预案：帧同步

> 定位：**状态同步（服务器权威广播 + 客户端预测/和解）是主路线**（M10 直接实现）；**帧同步降为预案**——预案的完整技术方案独立成篇：**《帧同步实施方案（预案）》**（含定点数全套、输入中继拓扑、影子 Sim 服务器）。本节只留对照与触发判据；切分支前先读预案文档。

### 12.1 两范式的业界对标（均为成功路线）

| 范式 | 业界对标 | 优劣 |
| --- | --- | --- |
| **状态同步（主路线）** | 荒野乱斗（俯视角竞技射击，服务器模拟+客户端预测）、LoL、OW、CS2 | 反作弊最强、无确定性长尾风险、FPS 扩展零切换；代价：增量快照/兴趣管理工程 + 每次改逻辑部署服务器 |
| **帧同步（预案）** | 王者荣耀、星际/魔兽系、GGPO 系格斗 | 带宽极低、逻辑改客户端即生效（迭代快）、确定性系统学习价值；代价：跨平台确定性长尾、回滚手感调参 |

### 12.2 帧同步预案的触发判据（命中任一才切分支）

1. **带宽扛不住**：状态同步快照经增量/兴趣管理优化后仍超预算（如大人数 >16、极密弹幕）——帧同步只广播输入，带宽是它的主场
2. **服务器迭代摩擦成为实际瓶颈**：玩法频繁迭代且每次部署服务器的成本不可接受
3. 若 FPS 扩展且选择帧同步形态（低带宽场景）

**M7–M9 投资在两范式下大部分复用**（Sim 结构 / 快照与回滚机制同构 / SimRng），**唯数值层例外**：帧同步分支需先补 **M7′——Sim 数值层 float→Q16.16 重写**（定点数全套设计见预案文档 §1：128 位乘、查表、溢出检测）。这是预案的**已知成本，约 1–2 周**，不是意外；切分支的总预算 = M7′ + M10′（网络层重做，见预案文档 §3）。**反过来说：只要帧同步预案未触发，float 就一直用下去，不做两套数值层共存。**

### 12.3 机制同构（当初决策的依据，保留存档）

帧同步 rollback 与状态同步的预测/和解是同一机制，重放范围不同：

| | 帧同步 rollback | 状态同步和解（主路线） |
| --- | --- | --- |
| 重放谁的输入 | 全体玩家 | 只有本地玩家 |
| 回退源 | 本地 SnapshotRing | 服务器权威快照 |
| 机制 | SnapshotRing + InputHistory + 重放 + View 重对齐 | **同一套** |

### 12.4 客户端形态（主路线定案）

客户端**仍跑同一套 `SimWorld`（预测形态）**，但信任模型反转：

- **本地玩家**：预测立即生效；服务器快照到达 → 对比 → 不符则回退快照、重放本地未确认输入（和解）
- **远端玩家**：**以服务器快照为准**（覆盖本地预测），快照间插值（30Hz 快照 → 60Hz 渲染插值）
- Sim 代码 / SnapshotRing / InputHistory / View 重对齐全套复用——帧同步客户端与状态同步客户端的差别只是"真相源从共识输入变为服务器快照"

### 12.5 警戒线（双向都成立）

范式切换必须是**显式的、有判据的分支**，不是顺手开启的开关：

- 状态同步为主时，**不得**因"想省带宽"悄悄改成纯输入广播——那是切到帧同步，客户端信任模型全变，必须走 §12.2 判据
- 若将来切回帧同步，**不得**保留状态广播兜底——两套真相源并存 = 谁都不权威

## 13. 数据归档与持久化

> 联机数据的"运行期 → 对局后 → 永久"三层。核心红利：确定性 Sim 让**归档不需要存状态**——「种子 + 输入 + 版本」即可重放整场对局，归档天然是完整证据链。

### 13.1 全景

| 数据 | 归属 | 载体 | 生命周期 | 落盘 |
| --- | --- | --- | --- | --- |
| 权威 `SimWorldState` | AuthSim | 内存（blittable 整块） | 对局期间 | 默认否 |
| `InputHistory`（服务器） | Room | 内存环形 | 对局 + 重连窗口 | **被标记即落盘**（§13.3） |
| `SnapshotRing`（客户端） | BattleContext | 内存环形 144 KB | 对局期间 | 否 |
| CommandBuffer / FrameEventBuffer | Sim | 定长数组 | **一帧** | 永不（每帧生命期，§5.1） |
| 输入日志录制 | M12 工具 | FileSys | 手动 | ✅ |
| 玩家偏好 | SettingService | FileSys 原子写 | 永久 | ✅ |
| 玩家进度/存档 | **见 §13.3 缺口 1** | — | 永久 | ⚠️ 权威化缺失 |
| Ops 指标 | RoomServer.Ops | 日志文件按天滚动 | 90 天 | §13.3 缺口 4 |

### 13.2 对局归档：一条记录 = 一整场对局

```csharp
MatchArchive {
    long Seed;  int[] Players;  string BuildHash;  string SimVersion;
    InputWire[] Inputs;          // 60Hz × 8 人，压缩前 ~1 KB/s，10 分钟对局 < 1 MB
    uint FinalChecksum;
}
```

- **产出时机**：对局正常结束 → 必归档；`ChecksumLedger`/客户端 `MismatchReport` 标记 → **立即落盘**（标记与存证绑在同一次写入，防服务器重启丢证据）。
- **用途**：复查重放（M12 离线工具直接吃归档文件）、战绩回放/观战（未来的免费数据源）、断线重连是同一条管线的运行期形态（§5.6）。
- **保留策略**：普通对局 7 天滚动清理；被标记/被举报的长期保留。
- **落盘实现**：服务器是 .NET 控制台，不能用客户端 FileSys（LiteFramework）——`Server` 侧自实现同款原子写（临时文件 + Replace，~30 行，Server 基础件之一）；按日期分目录，`{date}/{matchId}.archive`。

### 13.3 四个缺口与处置

| # | 缺口 | 处置 | 时机 |
| --- | --- | --- | --- |
| 1 | **玩家进度权威化缺失**（联机作弊洞，§10.12）：对局产出的经验/货币/物品掉落必须落服务器侧，当前客户端 FileSys 自持 = 客户端权威 | **进度变更单**：结算 → 服务器产出变更 → 独立**进度/存档服务**持久化（这是 §4.6"新增服务进程"的第一个真实入口，Fantasy 的 MongoDB 组件是该服务的候选之一）；MVP 降级：对局服落 JSON 文件定时归并；客户端本地 FileSys 降级为**镜像缓存 + 玩家偏好** | **上线前必做**，MVP（朋友局）豁免 |
| 2 | **结算落地无设计**：胜负/击杀/比分的持久化路径零字 | 与缺口 1 同一块：结算记录随进度变更单走，`MatchArchive` 存证 | 同上 |
| 3 | **InputHistory 纯内存**：对账标记后服务器重启 → 证据丢失 | "标记即落盘"（§13.2 产出时机），不落盘普通对局 | **M12** |
| 4 | **Ops 指标无持久化**：和解率/快照大小/丢包率没有时间序列，看不见"和解率从上周开始恶化" | 日志文件按天滚动（MVP） | **M12** |

**分层归属一句话**：运行期状态归内存（AuthSim / Ring / 帧缓冲）；对局事实归 `MatchArchive`（种子 + 输入 = 整场）；玩家事实归**服务器侧进度服务**（客户端 FileSys 永远只是缓存）；运维事实归滚动日志。四层各归各，任何一层试图兼任另一层（尤其客户端 FileSys 兼任玩家事实）都是 §10.12 级别的洞。

## 14. 联机策略化：俯视角 3D 射击与 FPS 双策略包（v3.4，2026-09-13 定案）

> 决策：**两个产品形态——俯视角 3D 射击联机与 FPS 联机——共用本文 §1–§6 全套底座，模式差异收进"策略包"（C#，装配期选择），不做两套管线。** 本文标题仍以俯视角射击为首发形态（M10 主路线不变）；FPS 是同一底座上的第二个策略实现，不是第二份文档驱动的第二套工程。

### 14.1 差异面盘点：什么进策略，什么绝不进

**共享底座（全模式同一套，禁止为模式分叉）**：Sim 核（`Step` 纯函数 / 槽位存储 / 双缓冲，§3）、KCP 双通道 + protobuf（§4）、RoomServer 权威 + 追帧 + 重连（§4.5/§5.6）、快照环 / 输入历史 / 回滚重放机制库（§5——"机制同一套，只是参数不同"，**策略就是那组参数的正式化**）、两层输入校验框架（§4.5）、AOI 网格底座（§3.8）。

**进策略的四个面**（都是引擎侧表现与参数，零玩法逻辑进 Lua，红线 5 不受影响）：

| # | 面 | 策略契约 | 差异内容 |
| --- | --- | --- | --- |
| 1 | 输入与预测 | 输入打包字段 + §5.3 预测标记表 | 俯视角 Move+自由朝向 vs FPS Move+视角逐帧量化 |
| 2 | 命中判定参数 | §3.4.1 回溯窗口开关与深度 | FPS 必回溯 133ms 档；俯视角即发即中可配、窗口可调小 |
| 3 | View 表现规则 | §6.1/§6.2 插值对象与本地直驱规则 | 俯视角全体统一插值 vs FPS 本地 0 插值直驱 + 远端插值 |
| 4 | 带宽与 AOI 旋钮 | SimConfig 参数 + AOI 过滤器选择 | 半径网格 vs 距离+视锥双裁剪；快照率与量化位宽 |

### 14.2 策略包形态与选择点

```csharp
// 落点：LiteSim.View（四个面全在引擎侧）。
// LiteSim.Core 不认识策略——SimConfig 旋钮由策略填充；LiteNet 不认识策略；Lua 不参与（热更红线 §10.4/5）。
public interface INetGameStrategy          // 一个包聚合四面，不散装四个接口（消费方一次装配）
{
    string ModeId { get; }                          // "topdown" / "fps"——Join 一致性校验对齐用
    void ConfigureSim(SimConfig cfg);               // 回溯窗口 / AOI 参数 / 快照率 / 量化位宽
    InputPack PackInput(in RawInput raw);           // 输入模型：打包字段 + 预测标记（§5.3 表由实现声明）
    IViewRule ViewRule { get; }                     // 本地直驱 / 插值 / 和解误差衰减规则（§6.1–6.2）
}
```

- 两个实现：`TopDownStrategy`（M10 首发）/ `FpsStrategy`（增量里程碑，暂记 **M13′**）。
- **选择点 = 构建级 / 启动配置**（2026-09-14 用户修订，原"装配期 + 房间参数 + 房间级 ModeId 混跑校验"作废，同步《联机同步策略设计》§0——**模式轴与范式轴同一粒度**）：构建配置决定 `(模式, 范式)` 组合，**一个构建只含一种组合**；RoomServer 启动参数 `--mode=` 选择；**Join 时 `ModeId` 并入 buildHash 一致性校验**（防跨构建混房间——退化为构建身份校验，不再有房间级混跑问题）。
- **不进 Lua Strategies 注册表**：网络层整体在热更红线外（§10.4——LiteSim.Core/LiteNet 不进热更程序集）；策略选择是装配期数据驱动，不是运行期 Lua 覆盖。Lua 侧经 `Bridge.sim` 只读快照消费，与模式无关。

### 14.3 两策略差异表（第二实现是接口的验收）

| 面 | 俯视角射击（TopDown，M10 首发） | FPS（M13′ 增量） |
| --- | --- | --- |
| 输入模型 | `MoveX/Z + AimX/Z`（朝向与相机解耦，自由瞄准） | `Move + Pitch/Yaw`（视角即输入，逐帧 zigzag 量化，位宽↑） |
| 预测范围 | §5.3 表原样：移动/朝向预测，**开火不预测** | 同左；开火**表现** 0 延迟（§6.2 viewmodel），命中判定仍不预测 |
| 命中判定 | 弹速快的即发即中可配；回溯窗口可调小 | hitscan **必回溯**（§3.4.1 全量 133ms） |
| View / 相机 | 固定俯角跟随（§6.2）+ 全体实体统一插值 | 第一人称相机（本地 0 插值直驱 + 远端插值），viewmodel 纯 View 层 |
| AOI | 半径网格过滤（§3.8 原样） | 距离 + 视锥（FOV）双裁剪 |
| 校验增量 | 移动 clamp + 射速表（§4.5） | + 视角变化率 clamp（防"甩枪瞬狙"） |

### 14.4 反通用化红线

- **M10 仍按俯视角交付**：`INetGameStrategy` 以 TopDown 单实现落地时接口即定形；**禁止**为"未来 FPS"预写分支、配置面或空实现（YAGNI 纪律同 §3.8 拒绝清单）。
- FPS 策略包 = M10 后增量（M13′）：复用机制库，预期工作量集中在输入量化、第一人称直驱规则、命中参数、视锥 AOI 四处——**不触碰 Sim 核与 LiteNet**；落地时允许修订接口（第二实现才是接口设计的验收）。
- 帧同步预案（§12）与策略轴**正交**：若预案触发，两个形态同受 §12 约束（数值层换定点数等），§14 的差异面划分原样适用。
