- 本文是**服务端唯一总设计**。旧文《联机服务端与运营层规划.md》已作废，其登录 / 大厅 / 持久化 / 社交 / 聊天设计全部并入本文。

## 2. 总体拓扑

```
  客户端 (Unity)
   │
   ├─ HTTPS / WebSocket ──► Gateway (YARP: TLS 终止 / JWT 校验 / 路由 / WS 终结转发)
   │   (大厅/账号/进度/社交/聊天)        │
   │                                    ├─ AuthService     登录 / 账号 / token 签发
   │                                    ├─ LobbyService    大厅 / 房间目录 / 匹配 / room_registry
   │                                    ├─ ProfileService  玩家进度 / 结算变更单（权威）
   │                                    ├─ ChatService     聊天 / 好友 / 社交（起步与 Lobby 同进程）
   │                                    └─ OpsCollector    指标（后置）
   │                                            │ Lobby → RoomServer Admin API (HTTP+JSON)
   │                                            ▼
   ├─ LiteNet (KCP/UDP, 直连不经 Gateway) ──► RoomServer 集群（多进程 · 多房间）
   │   权威 Sim 60Hz + 双通道 + 增量快照 30Hz + AOI + 预测/和解/回滚 + lag comp
   │                                            │
   └────────────────────────────────────────────┴─► ProfileService（结算变更单）
```

**关键路由原则**：客户端 ↔ 非战斗服走 **HTTPS/WS**（统一经 Gateway）；客户端 ↔ 战斗服走 **KCP/UDP 直连**（地址由 LobbyService 下发，**不经 Gateway**，否则 UDP 实时流被代理拖垮）。

> **与旧文拓扑的差异**：① 新增 Gateway 统一入口（TLS 终止 + JWT 校验 + WS 转发）；② 非战斗服含 WebSocket 推送；③ `MatchMaker` 归入 `LobbyService`（不再单列）；④ 不引入 gRPC / RabbitMQ（MVP）。

## 3. 协议矩阵（最终）

| 链路 | 协议 |
|------|------|
| 客户端 → 非战斗服（请求/响应） | **HTTPS + JSON** |
| 客户端 ← 非战斗服（推送：聊天 / 好友 / 匹配结果 / 系统通知） | **WebSocket**（经 Gateway 终结转发） |
| 客户端 ↔ 战斗服 | **LiteNet：KCP 双通道 + protobuf**（§4 已锁定，单源） |
| 服务 → 服务（同步，如 Lobby → RoomServer Admin API） | **HTTP + JSON**（MVP） |
| 服务 → 服务（异步） | **暂无**（MVP 无 MQ；将来上 RabbitMQ） |
| 战斗协议 | **protobuf 单源，禁双写**（红线） |

## 4. 服务分层与职责

| 层 | 服务 | 技术 | 职责 |
|----|------|------|------|
| **接入层** | Gateway | YARP + JWT 中间件 | 客户端统一入口、TLS 终止、token 校验、**WS 终结与转发**；**战斗 UDP 流不放行** |
| **账号** | AuthService | .NET | 游客/正式登录、账号、**token 签发**；与战斗服 `Join(token)` 验签打通 |
| **大厅** | LobbyService | .NET | 大厅、房间目录、**匹配**（含 `room_registry`）、房间创建 → 调 RoomServer Admin API |
| **进度** | ProfileService | .NET → MongoDB | 玩家进度与结算变更单（**权威**）、幂等落库；客户端 `FileSys` 只是镜像缓存 |
| **社交/聊天** | ChatService | .NET | 好友、私聊/世界/系统频道、敏感词过滤；起步与 Lobby 同进程 |
| **运维** | OpsCollector | .NET（后置） | 指标汇聚（和解率、房间数、在线、快照大小/丢包） |
| **对局** | RoomServer | .NET 控制台（`LiteNet` + `LiteSim.Core`） | 权威 Sim、增量快照广播、预测/和解/回滚、延迟补偿、AOI（**§10 锁定，不重画**） |

**跨服务通信**：MVP 同步调用走 **HTTP + JSON**；异步事件（战斗结算 → 进度写分）MVP 用**同步调用直推**，MQ 留作后续。

## 5. 账号与 token 链路

token **自包含**是"对局服保持薄"的关键——RoomServer 本地验签、**不查库、不认识账号**。

```
① Client → AuthService.Login(deviceId | credential)
② AuthService 校验/建号 → 签发 token（含 playerId + 过期 + 签名；HMAC/Ed25519）
③ Client 持久化 token（FileSys，降级为"镜像缓存"的既有纪律）
④ Client → RoomServer.Join(roomId, token, buildHash)
⑤ RoomServer 本地验签（持公钥/密钥，不查库）→ 通过进房
⑥ 断线重连：token 复用（或换取短时重连票据，见 §7 重连）
```

- **token 不进 Sim**（不参与确定性）；`buildHash` 校验照旧（防跨构建混房）。
- 账号形态：**游客账号（MVP）** 用 `deviceId`；正式账号（Steam/微信/Apple）经 `IAuthProvider` **策略位**后置接入，不动主流程。

## 6. 大厅 / 房间 / 匹配（含 room_registry 机制）

### 6.1 房间创建

```
Client → LobbyService.CreateRoom(mode, sync, capacity)
  → LobbyService 按 room_registry 选一个健康 RoomServer 进程（负载最低）
  → 调该进程内部 Admin API: POST /rooms {mode, sync, capacity}
  → 返回 {roomId, joinToken} → LobbyService 登记 room_registry
  → Client 用 (roomId, joinToken) 走 LiteNet Join（RoomServer 验签）
```

- RoomServer 的 Admin API **只做房间生命周期**（创建/销毁/查询），不认识账号、不查库。
- 健康检查：LobbyService 心跳各 RoomServer；心跳超时 → `room_registry` 标记不可用。

### 6.2 room_registry（本次定的机制）

| 阶段 | 载体 | 说明 |
|------|------|------|
| **MVP** | **进程内内存** | 非战斗服单机多进程起步，注册表偶有丢失可接受（重启即重扫） |
| **规模化** | **Redis** | 多实例 Lobby 共享房间目录；带 TTL，RoomServer 重启 → 条目超时淘汰 |

- 记录字段：`room_id / process_endpoint / mode / sync / capacity / player_count / state / updated_at`。
- **房间不跨进程迁移**（既定）：房间若因进程重启失效，对局中断，按 §10 重连语义不可恢复时提示重开。

### 6.3 房间发现与匹配

| 能力 | MVP | 后置 |
|------|-----|------|
| 发现 | **房间号 / 好友码**直连 | 房间列表（按 mode / 延迟排序） |
| 匹配 | 手动（好友码） | **快速匹配队列**（按 `(mode, sync, MMR)` 分桶，满员建房，在 LobbyService 内） |
| 组队 | 好友码邀请 | 队伍表 → 同队进同一房间 |

## 7. 数据层（统一 MongoDB + Redis）

> 2026-09-15 由「按数据形态分层」改为**统一 MongoDB**。旧文 §3.4 曾主张按形态选型（默认 PG / SQLite），此处**显式覆盖**：统一文档库换取开发与运维的单一心智；代价是结算幂等不再靠 PG 的天然约束，改用 Mongo 唯一索引 + 多文档事务（见下）。

| 数据 | 载体 | 生命周期 |
|------|------|----------|
| 账号 / 玩家进度 / 流水 | **MongoDB**（`player` / `playerProgress` / `progressLedger`） | 永久 |
| 好友 / 聊天消息 | **MongoDB**（`friend` / `chatMessage`） | 永久 |
| 对局归档元数据 | **MongoDB**（`matchArchive`） | 永久 |
| 对局归档大 blob（≈1MB/场） | **GridFS**（`fs.files` / `fs.chunks`，与元数据同库） | 普通 7 天滚动，被标记长期保留 |
| room_registry / 会话 / 在线 / 排行榜 | **Redis** | TTL |
| Ops 指标 | 滚动日志 →（后置）时序库 | 90 天 |
| 客户端本地 | 客户端 `FileSys`（偏好 + 镜像缓存） | **永不权威** |

**集合（草案，MVP）**

```js
player          { _id: playerId, deviceId, nickname, avatar, createdAt, lastLoginAt }   // deviceId 建唯一索引
playerProgress  { _id: playerId, exp, level, currency, updatedAt }                       // 当前值
progressLedger  { _id, playerId, matchId, delta, createdAt }                             // 唯一索引 {playerId, matchId}
matchArchive    { _id: matchId, seed, players, buildHash, simVersion,
                  finalChecksum, gridFsId, flagged, createdAt }
friend          { _id, playerId, friendId, state, createdAt }                            // 唯一索引 {playerId, friendId}
chatMessage     { _id, channelId, senderId, content, createdAt }                          // 后置；房间频道可不落库
```

- **结算幂等**：`{ playerId, matchId }` 唯一索引 + "先写流水、后改余额"——两步放同一 **MongoDB 多文档事务**（需 4.0+、**副本集**，故 MVP 也要把 Mongo 起成单节点副本集）→ 重复提交只落一次、可重放修复。
- **备份**：`mongodump` 按日备份；GridFS 随库一并备份。

## 8. 结算链路（本次定：直推）

```
RoomServer 对局结束 → 计算 progressDelta（经验/货币/胜负/比分）
  → HTTP 调 ProfileService.Apply(playerId, matchId, delta)   ← 同步直推
  → ProfileService 幂等写入（先流水后余额）→ 返回结果
RoomServer 同时将 MatchArchive（种子+输入+buildHash+FinalChecksum）写入 MongoDB（元数据）+ GridFS（blob）
```

- 结算（胜负/伤害/比分）**以权威结果为准**，客户端只做展示。
- 被标记 / 被举报对局 → `InputHistory` **立即落盘**（标记与存证同一次写入，防服务器重启丢证据）。
- 将来若"写分"出现削峰需求，再把这步改成异步经 RabbitMQ（届时只换传输，不改语义）。

## 10. 战斗服（锁定引用，不重画）

完整设计见《状态同步实施方案.md》§4 / §9 / §13，本文只收口：

- 传输 **kcp2k**（纯 C#、MIT，vendor 进 `Assets/LiteNet/Vendor/kcp2k`），不自研 KCP。
- 双通道：`Reliable`（信令 / 结算 / 重连）/ `Unreliable`（逐帧输入，裸 UDP + 冗余，每包带最近 4 帧输入）。
- 权威 Sim 60Hz（同一份 `LiteSim.Core`，纯 C# 零依赖，.NET 8 直接跑），增量快照 30Hz 广播 + **AOI 网格过滤**；客户端预测 / 和解 / 回滚；命中延迟补偿 = 服务器回溯。
- `buildHash` 版本校验（Join 比对）、输入两层校验（传输层挡非法 + Sim 内 clamp）、**和解率**为首要健康指标。
- `Protocol/`（纯函数打包解包）与 `Transport/`（kcp2k 收发）分层；`SnapshotDiffer` / `InputHistory` / `Relay` 自研约 600 行，**不用 Fantasy**。
- 部署：.NET 8 控制台，单进程多房间，每房间单线程 Sim；多进程水平扩展，由 LobbyService 分配。

**增强项（2026-09-15 采纳，叠加在《状态同步实施方案》§4 基线之上）**

| # | 增强 | 解决什么 | 时机 |
|---|------|----------|------|
| E1 | **慢客户端背压 + 降级** | 基线"快照尽力广播"无背压——一个慢客户端会拖垮房间。加 per-client 发送队列上限，超限按「降快照率 → 收缩 AOI → 丢低优先级实体」逐级降级 | M10 起带；上线前必备 |
| E2 | **快照优先级调度** | 基线全员全实体统一 30Hz。改为按「距玩家距离 / 最近是否变化 / 是否可见」分档降频，带宽与体验双赢 | M10 之后调优 |
| E3 | **握手 / 抗放大加固** | 基线只有 token + buildHash 校验。补连接 cookie（防 UDP 放大）、per-IP 限速、重连**一次性票据** | M10 起带 |

> 这三项是**机制补强**，不改范式、不动协议单源红线。

## 11. 可观测性与合规

- **指标**（OpsCollector 汇聚）：房间数、在线、快照大小/间隔、丢包率、**和解率**（客户端 `MismatchReport` 上报）。
- **日志**：按天滚动；归档与数据库按日备份。
- **版本对齐运维**：`buildHash` 校验 + `StartGame` 时 Sim 版本比对；这是"换服务器框架"时重建成本最高的部分（一两周），故 MVP 不做更重的预埋。
- **合规**（demo 阶段不阻塞，上线前必评审）：设备 ID 采集告知、聊天内容留存与隐私策略。

## 12. 部署形态

- **MVP（单机多进程）**：一台主机 / 容器内跑 Gateway（YARP）+ 非战斗服务（一个 ASP.NET Core 应用以 Hosted Service 托管 Auth / Lobby / Profile / Chat，或拆成几个小容器）+ **N 个 RoomServer 控制台进程**；**MongoDB（单节点副本集，为多文档事务）** + 归档走 GridFS；Redis 暂不引入（room_registry 走内存）。
- **演进**：Docker Compose → K8s（RoomServer 用 StatefulSet 管 fleet，非战斗用 Deployment，MongoDB / Redis 用托管或 Operator）。
